# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Freeloop is an open-source desktop app for macOS, Windows and Linux for running AI coding agents with the user's own models, switchable harnesses, Agent Skills, MCP servers and custom environments, built for someone who runs many sessions across many repos at once. Claude Code is the UX inspiration, not the base: the built-in harness is the product, and Claude Code is one external harness among several.

Status: M0 to M2 and nearly all of v1 are built; real-provider runs and a first release are what remain open. `docs/ROADMAP.md` lists what each milestone covers, where each feature lives and what is next. The documents in `docs/` are the specification. When this file and a document disagree, the document wins; fix this file.

## Read first

- `docs/ROADMAP.md`: milestones M0 to M3, each listing the requirement IDs it delivers and a definition of done. Find the current milestone before starting work; its "Not in" line says what to leave alone.
- `docs/DEVELOPING.md`: how the code fits together and how to add a provider, harness preset, environment or event type.
- `docs/ARCHITECTURE.md`: stack and alternatives, component diagram, Go interface sketches for Provider, Harness, Environment, Skill, Session and the permission broker, event schema, data layout, repository layout.
- `docs/REQUIREMENTS.md`: requirements with IDs such as `PRV-001`, priorities MVP / v1 / later, and acceptance criteria written to be testable.
- `docs/OPEN_QUESTIONS.md`: open decisions with a recommendation and the milestone they block; closed decisions with dates.
- `docs/SECURITY.md` (threat model), `docs/RISKS.md`, `docs/VISION.md`.

## Settled decisions (do not reopen without the user)

- Go core; Wails v3 (pinned to v3.0.0 in `go.mod` and `WAILS_VERSION` in the Makefile); React + TypeScript frontend built with Vite, npm as the package manager; macOS 14 on Apple Silicon (OQ-021), Windows 10 1809+ and Linux with WebKitGTK 4.1, both on x64 and arm64, working essentially the same (OQ-045, NFR-XPLAT-003). Commands run through zsh on a Mac, the login shell on Linux and Git Bash on Windows (OQ-019, OQ-043); Windows has no native sandbox yet (OQ-044).
- The engine runs in-process behind a transport-agnostic API until v1; the daemon split is EXT-004.
- SQLite through a pure-Go driver for index and metadata, one append-only JSONL file per session for transcripts, YAML for config, secrets only in the system keyring (macOS Keychain, Windows Credential Manager, Linux Secret Service) behind the `Secrets` interface.
- ACP (Agent Client Protocol over stdio) is the harness protocol. MCP goes through the official Go SDK targeting the 2026-07-28 revision. Skills use the Agent Skills `SKILL.md` format. Project instructions come from `AGENTS.md` first, `CLAUDE.md` as fallback, both read-only.
- Apache-2.0. No telemetry; the only outbound traffic is to user-configured endpoints plus an opt-in update check, a pinned token optimizer download the user clicks, voice input's pinned speech model (and, on Windows and Linux, whisper.cpp) when the user downloads it, and the MCP registry when the user browses it.

## Hard rules

- **Vendor boundary (HRN-008).** The app never reads, stores, proxies or forwards vendor OAuth tokens or session cookies. A subscription is used only by spawning the unmodified vendor binary, which performs its own sign-in. The built-in harness uses API keys and local endpoints only. Vendor names appear in plain text, never as logos or in the product name.
- **One chokepoint (SEC-003).** Every side effect from every harness passes through the permission broker. Nothing auto-approves on timeout. Deny rules win at every scope; project-level config can tighten but never loosen.
- **Everything through `Environment` (ENV-001).** No `os/exec` and no direct file I/O in the engine outside `internal/environment`; a lint rule enforces it. External agents' `fs/*` and `terminal/*` protocol requests go through the same layer, so protected paths hold for them too.
- **The GUI never special-cases a harness (HRN-001).** If a feature seems to need harness-specific UI, the `Harness` interface is wrong; fix the interface.
- **No in-process plugins.** Extension points are files (profiles, rules, presets, skills) and processes (ACP harnesses, MCP servers, hooks).
- **No system-specific code outside `internal/platform/{darwin,linux,windows}`** and the per-system files of `internal/environment` (NFR-XPLAT-002). The engine runs on all three systems; a feature that works on one must work on the others, or say why it cannot.
- **Never write into `~/.claude` or a project's `.claude/`.** Imports from Claude Code are one-way copies with provenance recorded.

## Architecture in brief

`internal/engine` is the only public surface; the Wails service layer and the JSON-RPC socket (`internal/rpc`) are thin adapters over it. `internal/engine/runtime.go` runs each session as a goroutine group under its own context and process group. A session is driven by a `Harness`: the built-in loop in `internal/harness/builtin`, or the generic ACP client in `internal/harness/acp` configured by a YAML preset (Claude Code is such a preset). Both produce the same versioned events (`schemas/events.json`, a strict superset of ACP `session/update`), both route permission requests through `internal/permission`, and both reach files and processes only through `internal/environment`. The `Store` writes every event to the session's JSONL before publishing it to the event bus and fsyncs dirty transcripts every 200 ms; the UI is a reducer over those events, so replay from disk and live streaming are the same code path. Providers are thin adapters over the official Anthropic, OpenAI and Google SDKs plus one OpenAI-compatible adapter; a per-model capability table (tool choice, parallel calls, stable call IDs) drives what the built-in loop attempts.

## Commands

Prerequisites: Go (Homebrew), Node with npm, Xcode command line tools, cmake (`make package` builds voice input's `whisper-cli` with it), and `make tools` once to install the pinned `wails3` CLI into `$(go env GOPATH)/bin`.

- `make dev`: run the app with live reload. It sets `FREELOOP_DEV=1`, which adds a scripted demo provider so the whole loop can be tried without an API key. Set `FREELOOP_HOME=/some/dir` to keep dev data out of the real data folder (`~/Library/Application Support/freeloop` on a Mac, `%AppData%\freeloop` on Windows, `~/.config/freeloop` on Linux).
- `make build` / `make package` / `make dmg`: production binary in `bin/` / ad-hoc signed `bin/Freeloop.app` / `bin/Freeloop.dmg` holding the app and a link to Applications. `make install`: quit Freeloop, rebuild it from this commit and leave that as the only copy (`INSTALL_DIR=`, `OPEN=1`; run it from a terminal, not from inside Freeloop). Every build is stamped with its commit (NFR-REL-006): Settings → Data, the problem report and the bundle's `FreeloopCommit` say it.
- `make windows-exe` / `make windows`: the Windows exes for amd64 and arm64 from any machine (pure Go) / plus an NSIS installer and a portable zip each (needs `makensis` and `zip`). `make linux-package`: the AppImage and `.deb` in the Docker image `build/linux/Dockerfile`, for Docker's own architecture unless `LINUX_ARCHS="amd64 arm64"`. `make release` builds what the host can (`RELEASE_PLATFORMS=mac` for the Mac alone).
- `make test`: Go tests under `internal/` and `cmd/` with the race detector, then frontend tests (`node --test`, no test framework). One Go test: `go test ./internal/<pkg>/ -run '^TestName$'`.
- `make check-app`: drive the real interface on the real engine in a real WebKit view, on scratch data with the demo provider (`scripts/appcheck.sh`, the steps in `scripts/appcheck/scenario.js`), then again on a lived-in data folder (`lived-in.sh`, `lived-in.js`); helpers in `lib.js`. Needs no key. Run it after a change to the interface.
- `make lint`: gofmt, `go vet`, the architecture boundary test (`internal/archtest`: ENV-001, Wails only in `cmd/freeloop`, macOS code only in `internal/platform/darwin`, cgo only there and in `internal/platform/linux`, the platform packages imported only by `cmd/freeloop`) and `tsc`. `GOOS=windows CGO_ENABLED=0 go vet ./internal/... ./cmd/...` checks the Windows build from any machine.
- `make release`: `bin/release` with the DMG (and the Windows and Linux packages the host can build), each with its SBOM (`internal/sbom`, `cmd/freeloop-sbom`), build information and checksums (SEC-012). `make verify-repro` builds a commit twice from clean clones and compares every file (NFR-SEC-004; `REF=<tag>`). `make verify-deps` checks modules against `go.sum` and that `go.mod` is tidy; a build no longer tidies it.
- `make memcheck`: package the app, run ten demo sessions in it on scratch data and check the idle footprint against 300 MB (NFR-PERF-004; the app's window opens while it runs).
- `make verify-agents`: run the HRN-005 scenario with each preset's real agent at its pinned version on a local stand-in model (HRN-007; downloads the agents, needs no key).
- `make test-keychain`: the Keychain backend against the real login keychain (creates and deletes one item under service `freeloop-test`).
- `make bindings`: regenerate `frontend/bindings` (git-ignored, regenerated by a build when its sources change) after changing a bound Go service.

## Working conventions

- Put the requirement ID in commit messages and PR titles, for example `SES-002: append-only JSONL writer`. IDs are stable; retire one with `(dropped)`, never renumber.
- When the implementation proves a document wrong, change the document in the same commit.
- A decision you cannot make from the docs goes into `docs/OPEN_QUESTIONS.md` with options and a recommendation; do not decide silently. Close a question with its outcome and the date.
- More than one Claude Code session may be working in this checkout at the same time. Stage only the files you changed; never `git add -A` or `git commit -a`.
- Ask before installing anything system-wide or adding a dependency; keep npm dependencies few and pinned.
- After pushing code, wait for CI (`gh run watch`) and say how it went; a red run is fixed before new work. CI's Linux and Windows jobs run on every push; the macOS job (build, lint, `make check-app`) runs on tags, weekly and by hand, so run `make check-app` locally after an interface change.
