Recommendation: GitHub Pages now, a project domain if one comes; the document lists the loopback redirect (`http://127.0.0.1/callback`, any port) and the `authorization_code` and `refresh_token` grants, and the app passes its URL as `ClientIDMetadataDocumentConfig`.

- **OQ-034 · How an SSH environment holds the project** · closed 2026-11-04 (the user asked for this model, and for it to be as secure as possible). A working copy per session on the other machine, kept in sync, with the project staying on this Mac: the app's git, diffs, checkpoints and worktrees keep working, about 80 uses of a local path need no change, and the other machine is a boundary an agent's commands stay behind. The other option, a project that lives only over there, suits repositories too big for a Mac and would need all of those reworked; it would be a new kind if asked for. The sync does not use rsync, which was the first plan: pulling from a machine that may be compromised would run rsync's receiver here against a hostile sender (CVE-2022-29154, CVE-2024-12086), so what comes back is a name list and a tar stream that Go reads as data. The other machine needs a POSIX shell, `tar` that takes `--null -T -` (GNU or BSD), `find`, `xargs`, and `git` if the copy should have a repository; BusyBox's `tar` is not enough. What it costs: only regular files come back with no executable bit, some files must be copied by hand, and a command's sync adds round trips.
- **OQ-031 · Is RTK worth having on by default** · closed 2026-11-03 (the user asked for the numbers again and took the recommendation). Off by default; it stays a per-session choice, with the pipe and `git log` exclusions. Measured on three sessions of 2026-11-03, 513 shell commands: 18 were rewritten, since 253 used a pipe and 183 were scripts of several lines, which are left alone on purpose, and none of the 96 test commands was among them; RTK's own log counted 231 of 130,929 tokens saved (0.18 %), nearly all from three `grep` calls, and the 57 file reads through it saved nothing. The first measurement, 2026-11-03 morning: 16 of 308 commands rewritten, 221 of 113,559 tokens saved (0.19 %). What would reopen it: a test-heavy session in which the agent knows RTK is on and the Info tab shows savings above a few percent.

- **OQ-046 · Git's system config on Windows · needed before a Windows release.** On a Mac and on Linux the app's own git calls and its push set `GIT_CONFIG_NOSYSTEM=1`, so a system-wide config cannot name a program for git to run (SEC-006). On Windows, Git for Windows keeps two things there that users rely on: `core.autocrlf=true`, without which every file checked out with CRLF line endings shows as changed, and `credential.helper=manager`, without which an https push cannot sign in. The system config lives under Program Files, which only an administrator can write. *Built 2026-11-08, waiting for the user's agreement:* on Windows the app reads the system config (`gitEnvFor`), and keeps hooks off by pointing `core.hooksPath` at a folder under `%SystemRoot%\System32` that does not exist (`/dev/null` would be read as `\dev\null` on the current drive, a folder anyone can make). Options: (a) as built; (b) keep `GIT_CONFIG_NOSYSTEM` and pass `core.autocrlf` and the credential helper through `-c` from what `git config --system` reports, which reads the system file but runs only the one named helper; (c) keep it, and accept the noise and an https push that fails. Recommendation: (b) if `git config --system --get credential.helper` names Git Credential Manager by its own path, otherwise (a), since the system file needs an administrator to change.

- **OQ-037 · The Linux sandbox · closed 2026-11-08 (the user chose bubblewrap, and for localhost the sandbox's own loopback with `pasta` when installed).** "Local, sandboxed" on Linux runs each command under bubblewrap (`bwrap`), as Seatbelt does on macOS. Seatbelt allows by default and denies; bubblewrap builds the command's view of the system from mounts, so each guarantee maps as follows. *Processes:* a private process namespace (`--unshare-pid`, `--new-session`), so no other program can be seen, signalled or read, and no terminal can be fed input. *Files:* the root read-only; the project, its caches and temp files writable (read-only in plan mode); the home folder replaced by an empty one with only the project, caches and listed toolchains mounted back; protected paths under the project mounted read-only; folders that must not be moved (`.git`) mounted on themselves, which makes renaming them fail; what is never readable (the data folder, a deny rule's paths) hidden under an empty folder or file, with the skill store mounted back. *Sockets:* `/tmp`, `/run`, `/var/run` and the home folder are fresh, so the Docker socket, the SSH agent, the D-Bus session bus and the keyring are out of reach; with no network, abstract sockets are too. *Network:* none is a private network namespace; all shares the host's; localhost is a private namespace whose loopback holds only what the sandbox starts, unless `pasta` (package `passt`) is installed, which then forwards the host's listening loopback ports into it, as on macOS; listed hosts reach the app's egress proxy through a socket mounted in and a bridge inside the sandbox. *Built 2026-11-08* (`internal/platform/linux/network.go`, `internal/environment/bridge_linux.go`), pinned to pasta 2024-02-20, Ubuntu 24.04's; Ubuntu 22.04 has no `passt` package. With pasta, a command runs as `pasta -q -f -t none -u none -T auto -U none -- bwrap ...`: pasta makes the network namespace and forwards the host's listening loopback TCP ports into it, checking each second, so a dev server started later is reached too; nothing is offered the other way; its interface stays down with no address or route (no `--config-net`), so nothing beyond loopback is reached. bwrap starts as root of pasta's user namespace, which owns that network, and could then bring the interface up, so it gets `--unshare-user --uid <user> --gid <group> --cap-drop ALL` (tried: without them, a command configured the interface). UDP is not forwarded, since a host's name server on loopback would let a command send data out by name lookups, which macOS's sandbox does not allow. That pasta does not start without a default route and warns on the command's output about a family with none, so the sandbox checks `/proc/net/route` and `/proc/net/ipv6_route` first, passes `-4` or `-6` when only one has a default route, and with neither, offline, keeps its own loopback (pasta from 2026 starts offline; the check is kept for 24.04's). The listed hosts with pasta reach the proxy as a forwarded port, as on macOS; without pasta, the app's proxy also listens on a Unix socket in `~/.cache/freeloop/egress/`, bound into the sandbox at `/run/freeloop/egress.sock`, and the app's own binary, bound at `/run/freeloop/bridge` and run with the hidden argument `sandbox-bridge`, binds `127.0.0.1:<the proxy's port>` inside, leaves a server for it behind (through a second process that exits, so the command is not its parent), and becomes the command, so the command keeps its exit status and signals. The bridge needs nothing installed. None has neither pasta nor the bridge. *Not carried over:* a protected path that does not exist when a command starts (a new `AGENTS.md` or git hook) cannot be mounted read-only, and a deny rule's wildcard covers only what matches when a command starts; the file tools still refuse both, and hooks and settings files still wait for approval, but a sandboxed shell command could create them. bubblewrap needs unprivileged user namespaces; where a distribution turns them off, or AppArmor withholds them (Ubuntu 24.04 grants `bwrap` its own profile), the environment's self-test fails and its commands do not run, as with a sandbox that cannot start on macOS.

- **OQ-029 · How token optimizers apply** · closed 2026-11-02 (the user asked for a dropdown and approved the plan after a test with RTK 1.1.0). By rewriting commands after approval, through the program's `rewrite` call, for the built-in harness first. `rtk hook claude` is not used: with a repository's `.claude/settings.json` allowing `Bash(*)` it answered "allow", and a `git push` ran with no approval, proven with the real Claude Code adapter. The program is not bundled, because the `rtk` edition carries a BUSL-1.1 engine and `rtk-oss` does not; the user installs it. It is off by default, because it can cut output an agent needs (`git log` bodies, large diffs). Reopened and extended 2026-11-03, when the user asked to install and use it from a Claude Code session. Claude Code now goes through a hook of Freeloop's own in the per-session plugin that calls `rtk rewrite`; since the agent then asks about the rewritten form, read-only commands use a narrow allow list (`permission.ReadOnlyCommand`). The app also offers to download `rtk-oss` 1.1.0, Apache-2.0, pinned by checksum, on the user's click, into its own caches; it still bundles nothing. Gemini CLI, Codex and OpenCode ran their shell tools without `terminal/create`, so that route serves only custom harnesses. Two more optimizers were tested on 2026-11-03, when the user asked for others, and neither was added; RTK stays the only built-in. squeez 1.49.2 (Apache-2.0) runs commands itself with `squeez wrap`, so it would need a new optimizer type. It answered a test run with a different failure with "~90% similar, output omitted" and a changed file with "identical, output omitted"; settings turn that off. What they do not turn off: a repository's `.squeez/filters.ini` hid a `git diff` line and changed `FAIL` to `ok`, and `git show HEAD:<file>` became `201 modified`.
