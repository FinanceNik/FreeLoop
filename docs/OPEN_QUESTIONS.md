# Open questions

Decisions not yet made, each with options, a recommendation and the milestone by which it must be settled (see [ROADMAP.md](ROADMAP.md)). Closed questions move to the bottom with their outcome.

## Open

- **OQ-016 · Plugin API shape beyond hooks · needed by v1.** Options: shell hooks only (EXT-005); JSON-RPC extension processes; WebAssembly plugins. Recommendation: hooks and ACP/MCP processes through v1; decide on a richer API only when a concrete need appears that those cannot meet.
- **OQ-017 · Contribution policy · needed before accepting PRs.** Options: DCO sign-off or a CLA. Recommendation: DCO, with `CONTRIBUTING.md` and a code of conduct added at v1 scoping.
- **OQ-024 · A Client ID Metadata Document for MCP sign-ins · needed by v1 release (MCP-006).** The MCP authorization spec prefers that a client identify itself by an HTTPS URL serving its client metadata (a Client ID Metadata Document); the app now registers itself with each authorization server through Dynamic Client Registration, or uses a client ID the user enters, because a metadata document needs a URL the project controls for as long as releases are in use. Options: host `client.json` on a project domain (stable, needs a domain and its upkeep); host it on GitHub Pages under the project's repository (free, tied to the repository's name); stay with registration only (works wherever the server allows registration, which some, such as GitHub's, do not). Recommendation: GitHub Pages now, a project domain if one comes; the document lists the loopback redirect (`http://127.0.0.1/callback`, any port) and the `authorization_code` and `refresh_token` grants, and the app passes its URL as `ClientIDMetadataDocumentConfig`.
- **OQ-018 · Other vendors' subscription terms** · closed 2026-11-04 (the user asked to settle it). Read at the source that day, by an engineer and not a lawyer, so this is a reading and not advice. **Gemini CLI: API key only.** Google's Gemini CLI terms (`docs/resources/tos-privacy.md` in its repository) say that directly accessing the services behind it through third-party software, "for example, using OpenClaw with Gemini CLI OAuth", violates its terms and "may be grounds for suspension or termination of your account". They do not mention another app starting the unmodified CLI, or ACP. Google sign-in for individuals and AI Pro and Ultra also stopped working in mid-2026. With an account at stake and no benefit left for most people, the preset says not to use it. Reading the pinned CLI (0.66.0) found the gap: over ACP it uses the login selected in the user's own `~/.gemini/settings.json`, whatever the preset says, so a session now warns when that is a Google login (`SignInCheck`, `internal/engine/signincheck.go`). The app reads only that choice, and does not change it. Not checked with a real Google account. **Codex: API key or the user's own ChatGPT sign-in, stated plainly.** OpenAI's authentication docs (`learn.chatgpt.com/docs/auth`) list the Codex CLI among clients that support ChatGPT sign-in, say "API keys are still the recommended default for automation" and "Use API key authentication for programmatic Codex CLI workflows", and do not mention third-party hosts. A maintainer wrote in `openai/codex` discussion 8338 that its terms and license are "quite permissive" and that OSS projects like OpenCode do similar things, and added "I'm an engineer, not a lawyer". OpenAI's Terms of Use could not be fetched (403); a search shows they bar "automatically or programmatically extract data or Output", and whether that reaches a host starting the CLI is unclear. So nothing permits this in writing and nothing found forbids it. The preset stays as the Claude Code pattern: the unmodified binary, its own sign-in, no token handling, `~/.codex/auth.json` never read. Its note says what is unknown and to use an API key for schedules. What would reopen this: either vendor saying anything about hosts starting its CLI. An Antigravity CLI preset is a separate later item.
- **OQ-030 · What a restore does with the guards its files leave out** · closed 2026-11-04 (the user asked to settle it). (a) and (c), as built, and not (b): a restore replaces settings, as the user asked, and does not merge this Mac's deny rules back. The preview lists what would stop applying before anything is written and the result lists it after, the replaced files are kept in `backups/`, and every restore through the app goes through the preview (`RestorePreviewed`). (b) would make restoring a backup to get rid of a rule quietly fail, and hooks have no such merge. It does not weaken the claim of 2026-11-03 in `docs/ROADMAP.md`, which is about the agent and the repository: a restore is the user's own act, and a backup someone else made shows its losses in red first. What would reopen this: a way for a restore to happen without that preview. *Related, settled the same day and easy to reverse:* allow rules written by hand in `rules.yaml` wait for approval like hooks, rather than applying on the next tool call as SET-001 first implied; an allow rule cannot tell a hand edit from a planted one.
- **OQ-034 · How an SSH environment holds the project** · closed 2026-11-04 (the user asked for this model, and for it to be as secure as possible). A working copy per session on the other machine, kept in sync, with the project staying on this Mac: the app's git, diffs, checkpoints and worktrees keep working, about 80 uses of a local path need no change, and the other machine is a boundary an agent's commands stay behind. The other option, a project that lives only over there, suits repositories too big for a Mac and would need all of those reworked; it would be a new kind if asked for. The sync does not use rsync, which was the first plan: pulling from a machine that may be compromised would run rsync's receiver here against a hostile sender (CVE-2022-29154, CVE-2024-12086), so what comes back is a name list and a tar stream that Go reads as data. The other machine needs a POSIX shell, `tar` that takes `--null -T -` (GNU or BSD), `find`, `xargs`, and `git` if the copy should have a repository; BusyBox's `tar` is not enough. What it costs: only regular files come back with no executable bit, some files must be copied by hand, and a command's sync adds round trips.
- **OQ-031 · Is RTK worth having on by default** · closed 2026-11-03 (the user asked for the numbers again and took the recommendation). Off by default; it stays a per-session choice, with the pipe and `git log` exclusions. Measured on three sessions of 2026-11-03, 513 shell commands: 18 were rewritten, since 253 used a pipe and 183 were scripts of several lines, which are left alone on purpose, and none of the 96 test commands was among them; RTK's own log counted 231 of 130,929 tokens saved (0.18 %), nearly all from three `grep` calls, and the 57 file reads through it saved nothing. Where the tokens went instead: about 528,000 from shell output and 500,000 from file reads, of which 50 of 585 tool calls made 43 %. An outside benchmark (daseinlabs/code-compression-bench, 100 SWE-bench Verified tasks on Sonnet 4.6, run by a company that does not say whether it has ties to the tools) had RTK at $3.07 per solved task against $2.58 with nothing and 54 solved against 57, so the lines it drops look to cost more than the tokens it saves. The first measurement, 2026-11-03 morning: 16 of 308 commands rewritten, 221 of 113,559 tokens saved (0.19 %). What would reopen it: a test-heavy session in which the agent knows RTK is on and the Info tab shows savings above a few percent.

- **OQ-038 · Where a workflow's issues come from · needed by v1 (WFL-004).** Options: (a) local Markdown files in the project's backlog folder; (b) GitHub issues through the GitHub CLI, as SES-017 lists them; (c) both as equals. Recommendation (the user's, and built so): (a) first, with GitHub as an import source later. Local files need no network or account, work in local-only mode, version with the code, and give the engine one place to read an issue's status from for every harness (HRN-001); an agent writes them with its ordinary file tools. GitHub issues need `gh`, a signed-in account and network, and an agent closing one acts outside the broker's file policy. An import would copy an issue's title, body and links into `backlog/issues/` and leave the issue open on GitHub.
- **OQ-041 · Where "Archive finished" puts finished PRDs and issues · needed by v1 (WFL-004).** Options: (a) `backlog/archive/` in the project; (b) out of the project, into the data folder (`archive/<project>/<date>/`), with `git rm` staging their removal; (c) delete them, relying on git history. Recommendation, and built so: (b). The point of archiving is that later agents are not misled by stale docs; anything left in the working tree can still be found by a search, while git history and the copy keep them. Only committed files are moved, so nothing unsaved is lost.
- **OQ-042 · How parallel AFK runs merge · needed by WFL-007.** Options: (a) one worktree per issue, merged by the app in dependency order, stopping at the first conflict; (b) a merge session: an agent merges the branches and runs the tests, asking as usual; (c) the user merges each from the Diff tab. Recommendation: (b), with (c) as what is left when the merge session stops; (a) cannot resolve a conflict, which is when it matters.

## Closed
- **OQ-039 · Where a workflow's backlog lives · closed 2026-11-08 (the user chose).** In a plain project folder, `backlog/prds/` and `backlog/issues/` by default, set per workflow, and not in `.freeloop/`: agents may never write inside `.freeloop/`, a rule the broker, both sandboxes and the SSH sync enforce, and an AFK agent must mark its issue done. The app still reads the backlog only in trusted projects.
- **OQ-040 · Where an AFK run works · closed 2026-11-08 (the user chose).** In one worktree and branch per run, shared by its sessions in turn, so the user's checkout and other sessions are not touched; the user merges the branch from the Diff tab after QA. The backlog must be committed before a run starts, since the worktree is made from the last commit.
- **OQ-037 · The Linux sandbox · closed 2026-11-08 (the user chose bubblewrap, and for localhost the sandbox's own loopback with `pasta` when installed).** "Local, sandboxed" on Linux runs each command under bubblewrap (`bwrap`), as Seatbelt does on macOS. Seatbelt allows by default and denies; bubblewrap builds the command's view of the system from mounts, so each guarantee maps as follows. *Processes:* a private process namespace (`--unshare-pid`, `--new-session`), so no other program can be seen, signalled or read, and no terminal can be fed input. *Files:* the root read-only; the project, its caches and temp files writable (read-only in plan mode); the home folder replaced by an empty one with only the project, caches and listed toolchains mounted back; protected paths under the project mounted read-only; folders that must not be moved (`.git`) mounted on themselves, which makes renaming them fail; what is never readable (the data folder, a deny rule's paths) hidden under an empty folder or file, with the skill store mounted back. *Sockets:* `/tmp`, `/run`, `/var/run` and the home folder are fresh, so the Docker socket, the SSH agent, the D-Bus session bus and the keyring are out of reach; with no network, abstract sockets are too. *Network:* none is a private network namespace; all shares the host's; localhost is a private namespace whose loopback holds only what the sandbox starts, unless `pasta` (package `passt`) is installed, which then forwards the host's listening loopback ports into it, as on macOS; listed hosts reach the app's egress proxy through a socket mounted in and a bridge inside the sandbox. *Not carried over:* a protected path that does not exist when a command starts (a new `AGENTS.md` or git hook) cannot be mounted read-only, and a deny rule's wildcard covers only what matches when a command starts; the file tools still refuse both, and hooks and settings files still wait for approval, but a sandboxed shell command could create them. bubblewrap needs unprivileged user namespaces; where a distribution turns them off, or AppArmor withholds them (Ubuntu 24.04 grants `bwrap` its own profile), the environment's self-test fails and its commands do not run, as with a sandbox that cannot start on macOS.

- **OQ-035 · How to show a PDF inside the app** · closed 2026-11-05 (the user chose it, after asking for a safe way that needs no other app). WebKit's own PDF view, in a frame inside a viewer frame whose Content Security Policy is `frame-src blob:` (`frontend/src/pdfview.ts`), with `blob:` added to the app page's own `frame-src` (`frontend/vite.config.ts`), since a frame's policies stack. That page's policy already keeps outside sites out of its frames but allows localhost, for the app preview, so the viewer's is what stops a link to this Mac. Tried in a real WKWebView with hostile PDFs and real clicks: WebKit draws a PDF only with no sandbox at all, since it counts as a plugin, and any `sandbox` on the frame leaves it blank. In the app's page with no frame around it, one click on a link replaced the whole page; in a plain frame, it took the frame elsewhere; under this policy, nothing left the file, for a link, a command-click, a link to `file://`, a custom scheme or an app, and a PDF's JavaScript did not run. What remains: a bug in Apple's PDF parser would run in the same web process as the app's page, which can call the engine. Not taken: a second web view, the same renderer in a process of its own, for that risk, but a native view over the page that can cover menus; `QLPreviewView`, which starts its own process but gives less control; PDFKit's `PDFView`, which parses in the app's own process; pdf.js, a new dependency. Reopen for the second web view if PDFs from untrusted repositories become routine.
- **OQ-033 · One Keychain item for all secrets** · closed 2026-11-04 (the user chose it, after 7 to 10 password prompts per rebuild). macOS asks per item and, for an ad-hoc signed app, per build (OQ-009), so the secrets now live together in the item `keychain://freeloop/vault`. The cost: permission for that item is permission for every secret, where it used to be one at a time. - **OQ-029 · How token optimizers apply** · closed 2026-11-02 (the user asked for a dropdown and approved the plan after a test with RTK 1.1.0). By rewriting commands after approval, through the program's `rewrite` call, for the built-in harness first. `rtk hook claude` is not used: with a repository's `.claude/settings.json` allowing `Bash(*)` it answered "allow", and a `git push` ran with no approval, proven with the real Claude Code adapter. The program is not bundled, because the `rtk` edition carries a BUSL-1.1 engine and `rtk-oss` does not; the user installs it. It is off by default, because it can cut output an agent needs (`git log` bodies, large diffs). Reopened and extended 2026-11-03, when the user asked to install and use it from a Claude Code session. Claude Code now goes through a hook of Freeloop's own in the per-session plugin that calls `rtk rewrite`; since the agent then asks about the rewritten form, read-only commands use a narrow allow list (`permission.ReadOnlyCommand`). The app also offers to download `rtk-oss` 1.1.0, Apache-2.0, pinned by checksum, on the user's click, into its own caches; it still bundles nothing. Gemini CLI, Codex and OpenCode ran their shell tools without `terminal/create`, so that route serves only custom harnesses. Two more optimizers were tested on 2026-11-03, when the user asked for others, and neither was added; RTK stays the only built-in. squeez 1.49.2 (Apache-2.0) runs commands itself with `squeez wrap`, so it would need a new optimizer type. It answered a test run with a different failure with "~90% similar, output omitted" and a changed file with "identical, output omitted"; settings turn that off. What they do not turn off: a repository's `.squeez/filters.ini` hid a `git diff` line and changed `FAIL` to `ok`, and `git show HEAD:<file>` became `201 modified`. With settings that keep everything, almost no saving was left outside those wrong answers. PTK 0.1.6 (MIT, on PyPI) has a `rewrite` command, but what it generates is `python -m ptk`, which ran a `typer.py` planted in the repository and does not start from a virtual environment. Its `git show HEAD:<file>`, `git diff --stat` and `git diff --name-only` came back empty with exit 0, `grep` kept 20 of 200 matches with no note, its repository returned 404 and it needs Python 3.11 or newer. Before adding either: squeez would need a way to turn off a repository's filters and correct `git show`; PTK, correct output and a maintained source.

- **OQ-022 · Virtualizing the transcript** · closed 2026-10-29. (a): the conversation keeps rendering every item with `content-visibility: auto`, which measured 226 ms to open a 5,001-event transcript and at most 1.7 ms of layout per scroll step in the built-in browser. The user checks scrolling in the packaged app on an M1; a virtualized list comes only if that misses 60 fps, and GUI-003 and NFR-PERF-002 are reworded to the measured targets once it passes. Correcting the scroll from a `ResizeObserver` arrives a frame late and still jumped by up to 840 px. Drawing each item once, 30 per frame from the end up (`drawOnce` in `frontend/src/scrollPlace.ts`), took about 200 ms and left none, at every speed, since WebKit then remembers its height. Found the same day, when the user reported that the view no longer followed a running agent: stopping on any upward scroll also caught the view moving by itself. In a real WebKit view, cards collapsing at the end moved it from 1730 to 1154 with no input, and following never came back. Now only the reader's input stops it (wheel, touch, scrolling keys, a held pointer), and the view follows every event and every change of the conversation's size. Measured the same day in a real WebKit view with `make check-app`, when the user reported it still went wrong: a 225-item transcript opened 926 px from its end and stayed there, since items grew from their placeholder after the jump; content growing with no event was not followed; a running turn showed frames up to 367 px behind, since the scroll came after the paint; and a wheel event that moved the conversation nowhere, a twitch or a scroll inside a code block, held the place for good. Now the view follows before each frame and whenever any item changes size, input going up only pauses it, and where the view ends up decides whether the place is held. A nudge within 60 px of the end keeps following, and a card opened to read holds the place.
