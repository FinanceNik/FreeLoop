# Requirements

Project: **Freeloop**. Status: M0 and M1 built, M2 and M3 work under way; see [ROADMAP.md](ROADMAP.md). Companion documents: [VISION.md](VISION.md), [ARCHITECTURE.md](ARCHITECTURE.md), [ROADMAP.md](ROADMAP.md), [RISKS.md](RISKS.md), [SECURITY.md](SECURITY.md), [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md).

## Conventions

- **ID**: `AREA-NNN`. IDs are stable; retired requirements are marked `(dropped)` rather than renumbered.
- **Priority**: `MVP` = in the first public release, `v1` = the first release meant for other people, `later` = after v1 or unscheduled.
- **Accept**: acceptance criteria, written so a test or a five-minute manual check can pass or fail them.
- Milestones that group these requirements into shippable slices are in [ROADMAP.md](ROADMAP.md). The thin vertical slice (M1) is a strict subset of MVP.

Decisions these requirements encode (from the planning interview, October 2026): macOS only for now; Go core, Wails shell, React/TypeScript frontend; the built-in harness is the base and Claude Code is one external harness; the app never touches vendor subscription tokens; sessions run across multiple repos concurrently; Claude Code style permission modes plus rules; secrets in the macOS Keychain; SQLite plus JSONL on disk; no telemetry; Apache-2.0.

## Functional requirements

### Providers and models (PRV)

- **PRV-001** · MVP · **Provider registry with built-in types.** Three provider implementations: Anthropic (native Messages API), OpenAI-compatible (generic chat completions with tools, with presets for OpenAI, OpenRouter, LM Studio, llama.cpp server, vLLM, Ollama's `/v1`), and Ollama native (for model listing and pull status). *Accept:* a user can add one provider of each type from the UI and see it listed; presets prefill base URL and required headers.
- **PRV-002** · MVP · **Add and test a provider.** Form with name, type, base URL, API key (stored per SEC-004), optional default headers. "Test connection" performs a minimal request. *Accept:* a wrong key or URL produces a readable error naming the provider; a correct one shows the models found.
- **PRV-003** · MVP · **Model discovery.** List models from the provider's endpoint where one exists; otherwise allow manual model IDs. Favorites and hidden models. *Accept:* after adding Ollama the locally pulled models appear within 2 s; a manual model ID can be used in a session without restarting.
- **PRV-004** · MVP · **Streaming completion with tool calling, normalized.** All providers stream text, tool calls (including streamed tool-argument deltas) and usage into the internal event schema (EXT-002). *Accept:* the same built-in harness session transcript is produced, modulo content, against Anthropic, OpenRouter and Ollama for a prompt that triggers one `read_file` tool call.
- **PRV-005** · MVP · **Model capability flags.** Per-model and per-provider: tool calling, `tool_choice` support, parallel tool calls, streamed tool arguments, stable tool-call IDs, structured output, vision, reasoning controls, context window, max output; auto-detected where possible (a tool-calling probe on first use for local models), user-overridable. *Accept:* choosing a model without tool calling for the built-in harness is blocked with an explanation; an override makes it selectable.
- **PRV-006** · MVP · **Switch model mid-session (built-in harness).** *Accept:* the next turn uses the new model; the transcript records the switch.
- **PRV-007** · MVP · **Token accounting per turn and session.** Input, output, cache read/write where reported. *Accept:* totals in the session header match the sum of per-turn usage.
- **PRV-008** · v1 · **Cost estimates.** Official list prices per model ship with the app (OQ-023) and an editable table comes before them; a call's long prompt and hour-long cache writes pay their own rates; session and per-day totals. An external agent's usage is counted the way it reports it, and said so: per model call with its model (Claude Code), or as a turn's total from its answer, priced by the model the agent says it is on (Codex CLI), or not reported at all (OpenCode), never shown as nothing spent. A model named with its provider or its effort (`openai/gpt-5.5`, `gpt-5.5/high`) finds the plain name's price. *Accept:* a session shows an estimated cost that updates per turn; a turn total with the agent's model setting is priced by it, and a session whose agent reports no tokens says "not reported by the agent"; `make verify-agents` checks what each pinned agent reports.
- **PRV-009** · v1 · **Prompt caching.** Use provider caching (Anthropic cache breakpoints; OpenAI automatic) for system prompt, skills index and tool definitions. *Accept:* cache-read tokens are non-zero on the second turn of a session against Anthropic.
- **PRV-010** · v1 · **Retry and fallback policy.** Exponential backoff on 429/5xx; optional fallback model per profile. *Accept:* a forced 429 is retried and surfaced as a non-fatal notice.
- **PRV-011** · v1 · **Reasoning controls normalized.** Effort/budget settings mapped per provider, thinking shown collapsed. *Accept:* changing effort changes the request payload for both Anthropic and OpenAI-compatible providers.
- **PRV-012** · v1 · **Native Google Gemini and OpenAI Responses providers.** For features the compatible layer cannot express. *Accept:* Gemini and GPT models can be used with tool calling without the OpenAI-compatible shim.
- **PRV-013** · later · **Out-of-process provider adapters.** For providers with unusual APIs (see EXT-007).
- **PRV-014** · v1 · **Model and effort in the session.** The session offers the model and effort it can use, beside the composer, the same controls for every harness: the built-in agent's from its providers, an external agent's from what it reports over ACP (`configOptions`, categories `model` and `thought_level` only). The next model call uses a choice, and it survives a restart; an agent that has not started says so and starts only when asked or at the first message. *Accept:* a choice reaches the model's API; after a restart the same choice is used; an agent's mode cannot be set this way.
- **PRV-016** · later · **Subscription value.** For each subscription the user declares in `config.yaml` (agent, name, monthly price), the usage page shows per calendar month the API-equivalent cost of that agent's work, the price, their ratio, a projection for the month so far, and the highest weekly limit reached. The app cannot tell a subscription from an API key without reading the sign-in, which it never does (HRN-008), so the user declares it. *Accept:* a $200 subscription and $640 of API-priced Claude Code usage in October show 3.2× for October; the current month shows the amount so far and a projection; with none declared the card links to Settings.
- **PRV-017** · v1 · **Budgets.** A budget is an amount of estimated spending per day or per month, in local time, for every session or one profile's, kept in `config.yaml` (`budgets`) and edited beside the prices. Its spending is the period's priced usage; what it cannot count, models without a price and turns an agent reported no tokens for, is said beside it. From 80% the usage page and the sidebar's cost show it and a notification comes, once per period and level; once reached, the queue starts no new task under it (SES-025). It never stops a running session. *Accept:* with a $10 daily budget, $8 of priced usage warns once however often it is checked, $11 says reached once and a queued task waits with the budget named; a budget for another profile counts none of it; `make check-app` sets one in Settings and sees it on the usage page.

### Harnesses (HRN)

- **HRN-001** · MVP · **One harness interface.** Every harness, built-in or external, exposes the same operations: create session, prompt, cancel, set mode, list capabilities, emit events. The GUI never special-cases a harness. *Accept:* the conversation, approvals and diff panels work unchanged for the built-in harness and for the Claude Code harness.
- **HRN-002** · MVP · **Built-in harness.** An agentic loop in Go with tools `read_file`, `write_file`, `edit_file` (exact string replace, multi-occurrence guard), `list_dir`, `glob`, `grep`, `shell` (through the session's environment, ENV-001), `load_skill` (SKL-004), and MCP tools (MCP-003). Stops on model end-turn, max turns, max tokens or cancel. *Accept:* "add a failing test for X then make it pass" completes against a repo with at least one edit and one shell call, each shown as a tool call in the transcript.
- **HRN-003** · MVP · **Declarative harness profiles.** YAML files defining: display name, harness (built-in or external), model and provider, system prompt template, enabled tools, permission policy (SEC-002), skills, MCP servers, loop limits, instruction-file policy. Profiles live in the app config dir and optionally in a project's `.freeloop/profiles/`. *Accept:* two profiles that differ in model and tool set can run side by side in two sessions; invalid YAML is reported with line and field.
- **HRN-004** · MVP · **Choose harness and profile at session creation.** *Accept:* the new-session dialog lists profiles grouped by harness, with the project's default preselected.
- **HRN-005** · MVP · **Generic ACP client.** Launch an external agent process by command, args, env and cwd; speak Agent Client Protocol over stdio; map initialize, session new/prompt/cancel, tool call updates, permission requests, plan and mode updates into the internal event schema; pass MCP servers (MCP-004); fulfil the agent's file-system and terminal requests through the session's environment. *Accept:* a reference ACP agent (the Gemini CLI or the ACP example agent) completes a prompt that reads and edits a file, with the edit approved through the app's approval UI.
- **HRN-006** · MVP · **Claude Code harness.** Preconfigured external harness that runs the unmodified Claude Code binary through its ACP adapter, with login performed by Claude Code's own flow and the app never reading, storing or forwarding its tokens (see HRN-008). *Accept:* a user signed in to Claude Code with a subscription runs a session from the app; the app's config and database contain no Anthropic OAuth token; permission prompts appear in the approval inbox.
- **HRN-007** · v1 · **Verified presets for other agents.** Gemini CLI (API-key authentication, since Google-account sign-in for individuals ended in mid-2026 and Google's terms speak against third-party access through one; a session warns when the agent's own settings choose it, OQ-018), Codex CLI (an API key or the user's own `codex login`), Goose, OpenCode, Copilot CLI (the user's own `copilot login` on a Copilot plan; in an untrusted project it does not start while the project has hooks for it, since it runs them itself, SEC-006): tested command lines, quirk handling, documented auth method. *Accept:* each preset passes the HRN-005 acceptance scenario (`make verify-agents`, with the real agent on a local stand-in for its model).
- **HRN-008** · MVP · **Subscription boundary.** The app never collects, stores, proxies or intermediates vendor OAuth tokens or session cookies; the only subscription usage is through an unmodified vendor binary performing its own sign-in. The built-in harness uses API keys and local endpoints only. *Accept:* a code search finds no OAuth handling for vendor consumer accounts; the Claude Code adapter does not pass credentials in env or args; documentation states the boundary.
- **HRN-009** · MVP · **Plan mode in built-in harness.** Read-only tool set until the user approves the plan. *Accept:* in plan mode a write attempt is refused and recorded; approving switches the session to the chosen mode.
- **HRN-010** · MVP · **Instruction files.** The built-in harness loads `AGENTS.md` from the project root (and nested, when files under that directory are touched); falls back to `CLAUDE.md` read-only when no `AGENTS.md` exists; profile system prompt is prepended. *Accept:* a rule stated only in `AGENTS.md` is visibly followed; the files are never modified by the app.
- **HRN-011** · v1 · **Custom code harnesses.** "New harness" scaffolds an ACP agent from a Python or Go template that already speaks the protocol, registers it, and supports restart-on-change. *Accept:* from the template to a working session in under 15 minutes, following the docs only.
- **HRN-012** · v1 · **Switch harness or profile mid-session.** Implemented as a new session seeded with a handoff summary and the same environment. *Accept:* the new session's first turn can answer a question about work done in the old one.
- **HRN-013** · v1 · **Context management.** Automatic compaction when near the model's context limit; manual compact; visible context meter. MVP behaviour: warn at 80 %, stop at limit. *Accept:* a long session continues past the raw context limit after compaction with the task still progressing.
- **HRN-014** · v1 · **Subagents and parallel tool calls in the built-in harness.** *Accept:* two independent `read_file` calls in one model turn execute concurrently; a subagent's transcript is viewable from the parent.
- **HRN-015** · later · **Harness marketplace or registry.** Discover community harnesses.
- **HRN-016** · v1 · **One task on several profiles, compared.** The new-session form can send one first message to two to four profiles at once, each in its own worktree; a compare view shows each run's status, changed files, lines, tokens and last reply, and keeping one archives the others. *Accept:* a task sent to two profiles makes two worktree sessions with the same message; the compare view shows both runs' changes; "Keep" leaves one active and archives the other with its worktree.
- **HRN-017** · v1 · **Web and to-do tools in the built-in harness.** `web_fetch` reads a public page as text, `web_search` queries a search endpoint the user configures, and `todo_write` keeps a to-do list the session shows. Fetching and searching ask through the broker every time unless a rule allows that exact URL or query, plan mode refuses them, and private addresses are refused. *Accept:* a fetch asks, then returns the page as text; `http://localhost` and a name resolving to a private address are refused; with no endpoint set `web_search` is not offered; local-only mode refuses both; a to-do list from the built-in harness or an external agent's plan shows above the message box.
- **HRN-018** · v1 · **Review by a second agent.** The Diff tab sends a session's changes to another profile: a read-only session in plan mode, listed under the first, in the same worktree. When it answers, its findings can be put in the first session's message box. *Accept:* the reviewer gets the diff and can read files but not change them; its reply reaches the first session's box only when the user asks.

- **HRN-019** · v1 · **Token optimizers.** A dropdown in the session header runs the session's shell commands through a program that shortens their output, such as RTK, and off again, from the next command on. The broker approves the command as the model wrote it; the optimizer is asked only afterwards, and a rewrite that adds anything to the command, or any failure of the program, runs the original. Only a plain line is rewritten, for tools the optimizer lists: where output feeds a pipe, a redirection or a substitution, shortening it would change the result, and some tools would run a copy in the repository instead. The transcript shows the original with what actually ran. The model is told once, on its next message after one comes on, that the program is at work and not to look for it or type its name; the transcript does not show this as the user's. The Info tab says how many shell commands were shortened and, where the optimizer reports it, how many tokens were saved. *Accept:* a session with an optimizer on does not report it as missing; an approval never shows the rewritten form; a rewrite with an operator, redirection or substitution the original lacks runs the original; a hung or missing program costs at most its time limit and one notice; `raw: true` runs a command as written; subagents and forks keep the choice; an external agent with no hook for this shows the optimizer as not available with the reason; what the program keeps goes when the session is deleted. A new session takes what it is asked for, then its profile's `optimizer:`, then the default in Settings; `off` beats the others, and a project's profile cannot choose one. Listing optimizers runs nothing, since another program can have the same name; checking or choosing one does, and asking for one that does not work refuses, while a default that stopped working still starts the session and its first command says so. Other optimizers are files in `optimizers/<id>.yaml`, which run only after the user approved them as they are, and any change to a file ends its approval. The install command is typed into a terminal and never run for the user. An optimizer can also name a build at a pinned version and checksum: one click in the session downloads it into the app's caches and turns it on, nothing else on the Mac sees it, and a download that does not match is not kept. A Claude Code session takes an optimizer through a hook in its per-session plugin: the command the agent asks about maps back to what the model wrote, so the broker judges and shows that, and a command that only reads does not ask because of the rewrite. If the user's agent settings already hold the optimizer's own hook, the session says so, since Freeloop neither changes that file nor can switch that hook off. Not in a container, which cannot reach the app's socket.
- **HRN-020** · v1 · **Hand off when stuck or out of allowance.** A session that is stuck offers to continue on another profile in one action, with the reason: its account limit reached (a `limit_update` rejected), the turn limit reached, the same tool failing three times in a row, two rewinds in a turn, or provider errors after retries. The offer names the profile it suggests: the session's profile's `onLimit` for a reached limit, else the user's choice for that agent on the Profiles page (`fallbacks` in `config.yaml`); with neither, it offers a list. Choosing by GUI-040's cheapest working profile waits for GUI-040. Taking it is HRN-012's handoff, plus the old session's open approvals ended, a link both ways, and the new session's first message continuing the old one's last request. A profile may set `onLimit: <profile>` to do this without asking when its limit is reached, which still asks for every tool call as usual. *Accept:* a Claude Code session whose 5-hour limit is reached shows "Limit reached: continue on <profile>?" and one click continues there with the handoff; with `onLimit` set it continues without the question and says so in both sessions; three failures of one tool in a row show the offer.
- **HRN-021** · v1 · **An agent asks the user.** An agent can ask 1 to 4 questions with options, each with what it means, one or several to pick, and room for an answer of the user's own, shown as a form on its card. An external agent asks through ACP form elicitation, which the app says it takes, so Claude Code's AskUserQuestion is on; the form goes on the agent's own call carrying the questions. The built-in agent has `ask_user` with the same form. A form goes through the broker and asks the user in every mode, bypass and plan included; its buttons are Send and Skip. A link to open (URL elicitation) is not offered. *Accept:* an engine test with the reference agent sees the form on its call and the answers reach it, and fails without the capability; a built-in test asks in bypass and plan mode; `make check-app` answers a demo agent's two questions with a choice, several picks and an own note, and the agent says them back.

### Skills (SKL)

- **SKL-001** · MVP · **Agent Skills format is native.** A skill is a folder containing `SKILL.md` with YAML frontmatter (`name`, which must equal the folder name, `description`, and the optional `license`, `compatibility`, `metadata` and `allowed-tools` fields per the spec) plus optional `scripts/`, `references/` and `assets/`. *Accept:* an unmodified skill from the user's `~/.claude/skills` loads without changes.
- **SKL-002** · MVP · **Discovery and toggles.** Skills are discovered from the app's skill store, from `.freeloop/skills/` in a project, and (read-only) from `.claude/skills/` and `.agents/skills/` in a project; each can be enabled globally, per profile or per project. *Accept:* the skills panel lists every skill with source, scope and an enable switch; a disabled skill does not appear in the model's skill index.
- **SKL-003** · MVP · **Import from Claude Code.** One-way copy from `~/.claude/skills` with provenance (source path, date) recorded; re-import shows a diff. *Accept:* importing twice does not duplicate; the original files are untouched.
- **SKL-004** · MVP · **Progressive disclosure.** The system prompt lists enabled skills by name and description only; `load_skill` returns the body; referenced files are read on demand; scripts run through the environment and the permission broker like any shell call. *Accept:* the system prompt size grows by less than 100 tokens per enabled skill; a script in a skill triggers a permission prompt unless allowed by rule.
- **SKL-005** · MVP · **Install from folder or zip.** *Accept:* dropping a folder onto the skills panel installs it after a preview of its frontmatter and scripts.
- **SKL-006** · v1 · **Install from git URL and update.** Pin to a commit; "check for updates" shows a diff. *Accept:* install, update and rollback each complete with the skill remaining loadable.
- **SKL-007** · v1 · **Authoring.** Create from template, open in external editor, validate frontmatter against the spec, test-run with a chosen model. *Accept:* validation flags a missing `description`; a test run shows whether the model picked the skill for a sample prompt.
- **SKL-008** · v1 · **Skills for external harnesses.** Best-effort projection of enabled skills into each harness's native discovery location, documented per adapter. *Accept:* an enabled skill is visible to the Claude Code harness in a session started from the app.
- **SKL-009** · later · **Skill registry browsing.** Search and install from public skill registries.

### MCP servers (MCP)

- **MCP-001** · MVP · **Manage servers.** Add stdio (command, args, env, secret refs) and Streamable HTTP (URL, headers) servers; enable per profile or globally; start, stop, restart; show health, negotiated protocol revision, tool list and last error. Targets the MCP 2026-07-28 revision (stateless, `server/discover`) through the official Go SDK, which also speaks the 2025-11-25 and 2025-06-18 revisions for existing servers. *Accept:* a stdio server and a remote HTTP server both show their tools within 5 s of enabling.
- **MCP-002** · MVP · **Import from Claude Code config.** One-way import of `mcpServers` from `~/.claude.json` and a project's `.mcp.json`, previewed before applying. *Accept:* imported servers work without edits; secrets found in env are moved to the Keychain and replaced by references.
- **MCP-003** · MVP · **MCP tools in the built-in harness.** Namespaced `mcp__<server>__<tool>`; tool descriptions passed to the model; results returned as tool results; permission rules apply by namespace. *Accept:* a rule `allow mcp__github__*` auto-approves those tools and nothing else.
- **MCP-004** · MVP · **MCP servers passed to ACP harnesses.** Enabled servers are provided on ACP session creation so external agents use the same servers. *Accept:* a server enabled in a profile is listed by the Claude Code harness in a session started with that profile.
- **MCP-005** · MVP · **Trust on first start.** Before a new server first runs, show the full command or URL and ask for confirmation; warn when the command fetches remote packages (`npx`, `uvx`, `docker run` of an unpinned image). *Accept:* no server starts without one confirmation per server configuration change.
- **MCP-006** · v1 · **OAuth for remote servers.** OAuth 2.1 authorization code flow with PKCE per the MCP authorization spec; client registration through Client ID Metadata Documents with Dynamic Client Registration as a fallback; issuer validation; tokens in the Keychain, one item per server. *Accept:* a remote server requiring OAuth is usable after one browser round trip.
- **MCP-007** · v1 · **Resources and prompts.** Attach a resource to the composer; run a server prompt as a slash command. *Accept:* a resource's content appears in the next user turn; a prompt with arguments renders a form.
- **MCP-008** · v1 · **Input-required round trips.** Under MCP 2026-07-28 a server asks for more input by returning an `input_required` result (the Multi Round-Trip Request pattern that replaced server-initiated elicitation); the request is shown in the approval inbox as a form and the original call is retried with the answers. Older servers' `elicitation/create` requests take the same path. *Accept:* a server that asks for a confirmation blocks until the user answers in the inbox, then completes.
- **MCP-009** · v1 · **Server registry browsing.** Search a registry the user chose and add a server from it. *Accept:* nothing connects before an address is set; a result fills in the add-server form pinned to a version, and it starts only after the usual confirmation.
- **MCP-010** · v1 · **Suggested servers.** The MCP servers page lists a few common servers, built into the app: GitHub, Linear, Sentry, Notion, Context7 and Playwright. Nothing is fetched or run until the user adds one; "Add…" fills in the usual form, which is saved and approved like any other server. Each says where it runs (at its vendor, or on this computer with the user's rights) and how it signs in. Remote ones are reached over https at the vendor's documented address; a local one runs one exact version, never "latest". No server that reads files directly is suggested, since it would go around the protected paths. A suggestion already set up, by ID, address or command, shows as added. *Accept:* a unit test finds every address https and every local one pinned; `make check-app` finds the six suggestions, adds Context7 through the form and sees it listed, and then shown as added.

### Environments (ENV)

- **ENV-001** · MVP · **Environment abstraction.** Every tool execution, file read or write, PTY and process launch goes through an environment interface providing exec, file system, PTY, env vars, secret refs and working directory. *Accept:* the built-in harness has no direct `os/exec` or file-system call outside the environment package (enforced by a lint rule).
- **ENV-002** · MVP · **Local environment.** A folder on this Mac, usually a git checkout; per-environment env vars, secret references, tool allow/deny list, default permission mode, default profile. *Accept:* a secret set on an environment is visible to a shell tool call as an env var and absent from the transcript.
- **ENV-003** · MVP · **Projects and sessions bind to environments.** A project is a repo path with a default environment; a session chooses an environment at creation. Several sessions may share one environment. *Accept:* three sessions on three repos run concurrently, each with its own cwd and env vars.
- **ENV-004** · MVP · **Secret injection.** Secrets are resolved from the Keychain at process start and passed as env vars (or temp files with 0600 mode when a tool needs a file); never written to config or transcript; redacted in logs by value. *Accept:* grepping the config dir and transcripts for a known secret value finds nothing after a session that used it.
- **ENV-005** · v1 · **Docker and devcontainer environment.** Run external harnesses and all tool calls inside a container; reuse `.devcontainer/devcontainer.json` when present; bind-mount the repo; forward ports; lifecycle (create, start, stop, rebuild). *Accept:* the HRN-002 scenario runs with every shell call executing inside the container, verified by `uname -a` output.
- **ENV-006** · v1 · **External harness inside an environment.** ACP over stdio tunnelled through `docker exec` (and later `ssh`). *Accept:* the Claude Code harness runs inside a devcontainer with its own login state.
- **ENV-007** · v1 · **Setup and health.** Post-create script, health check, "environment is unhealthy" state surfaced on the session. *Accept:* a failing health check blocks new sessions with a reason.
- **ENV-008** · v1 · **SSH remote environment.** A session's commands run on another machine through the system's `ssh`, in a working copy kept in sync with the project, which stays on this Mac. The other machine and what runs on it are not trusted. So far with the built-in agent; an external agent over SSH is ENV-006's later half. *Accept:* with a real sshd, a command runs in the working copy and what it changes comes back; an unknown host key refuses to connect; no value of the environment appears on a command line on either side or in a file over there; secrets, what a deny rule covers and what the project ignores are not copied; a crafted tar stream writes nothing outside the project and makes no link, device or executable bit here; `.git`, `.claude`, `AGENTS.md` and other settings this Mac or an agent would act on do not come back, in any spelling APFS treats as the same; an edit here is not overwritten; a mass delete is not applied; a denied command does not run; local-only mode refuses another machine, also while a session runs.
- **ENV-009** · v1 · **Sandboxed local execution.** Restricted file-system and network for the shell tool without Docker: Seatbelt on macOS, bubblewrap on Linux (OQ-037); none yet on Windows (OQ-044). *Accept:* in a sandboxed environment a command writes in the project and runs its tests without an approval; it cannot write outside the project or to `.git/config`, `.git/hooks` or `.freeloop/`, read `~/.ssh` or `~/Documents`, reach the internet, or start another app; leaving the sandbox always asks; if the sandbox cannot be applied, commands do not run.
- **ENV-010** · v1 · **Network policy per environment.** A sandboxed environment can list the hosts its commands reach. *Accept:* with `registry.npmjs.org` listed, `npm view` works and `curl https://example.com` is refused and reported; a command ignoring the proxy gets no connection.

### GUI and UX (GUI)

- **GUI-001** · MVP · **Main window.** Left sidebar of projects, each expanding to sessions with their status (running, waiting for you, idle, error) as a dot before the title, named in its tooltip; center conversation; right panel with tabs Diff, Approvals, Info. *Accept:* every session state is distinguishable in the sidebar without opening it.
- **GUI-002** · MVP · **Attention view.** A list of every session waiting for approval, input or in error, across all projects, with inline approve/deny and one-click jump. *Accept:* with five sessions prompting at once, all five can be resolved from the attention view without opening each session.
- **GUI-003** · MVP · **Conversation rendering.** Streaming markdown, code blocks with copy, collapsible tool calls showing input and output, inline diffs for edits, collapsed thinking, visible turn boundaries and timestamps. *Accept:* a 5,000-event transcript scrolls at 60 fps on an M1 (virtualized list).
- **GUI-004** · MVP · **Composer.** Multiline input, `@path` file mentions with fuzzy picker, slash commands for profile-defined prompts and mode changes, message queueing while the agent runs, cancel. *Accept:* a message typed while the agent runs is sent at the next turn boundary; cancel stops within 1 s.
- **GUI-005** · MVP · **Diff and commit panel.** Changed files versus the session's base commit; per-file diff; stage, commit with message (AI-suggested, editable), discard file. *Accept:* a commit made from the panel appears in `git log` with the chosen message.

- **SES-003** · MVP · **Restore on restart.** Sessions reopen in an idle state with full history; external harness sessions resume via ACP session load where the agent supports it, otherwise a new agent session is seeded with a summary. *Accept:* after restart, a continued prompt in a built-in session has the prior turns in context.
- **SES-004** · MVP · **List, filter, auto-title.** Filter by project, status, harness, date; titles generated from the first exchange, editable. *Accept:* a session is findable by its title within one filter step.
- **SES-005** · MVP · **Archive and delete.** Archive hides; delete removes the transcript and database rows after confirmation. *Accept:* a deleted session's files are gone from disk.
- **SES-006** · MVP · **Git state per session.** Branch, HEAD, dirty file count shown live; base commit recorded at session start for the diff panel. *Accept:* the diff panel still shows the session's changes after an unrelated commit on the same branch.
- **SES-007** · v1 · **Full-text search across sessions.** *Accept:* a phrase from a tool result three weeks old is found in under 1 s.
- **SES-008** · v1 · **Export.** Markdown and JSON export of a session. *Accept:* the Markdown export renders tool calls and diffs legibly.
- **SES-009** · v1 · **Fork from a message.** *Accept:* the fork has the history up to that message and a new transcript file.
- **SES-010** · v1 · **Worktree per session (opt-in).** Create a worktree and branch at session start, clean up on archive, merge-back or PR helper. *Accept:* two sessions on the same repo edit the same file without interfering.
- **SES-011** · v1 · **Pull request creation.** Through the GitHub CLI with an AI-drafted, editable description. *Accept:* the PR URL appears in the session after creation.
- **SES-012** · v1 · **Scheduled and recurring sessions.** A schedule starts a new session in a project with a prompt hourly, daily, on weekdays or weekly while the app runs; each run goes through the permission broker like any session. *Accept:* a due schedule starts one session tagged `scheduled` with its prompt; a run missed while the app was closed runs once when it opens; a run that needs an approval waits for it.
- **SES-013** · v1 · **Tags and saved filters.** Sessions carry tags; the sidebar filters by tag (from a menu or `#tag` in the search box) and keeps named filters. *Accept:* a tag added in one session shows in the sidebar at once, filtering by it lists only tagged sessions, and a saved filter returns after a restart.
- **SES-014** · v1 · **Checkpoints and rewind.** Before a turn changes files, the session's working tree is snapshotted; any user message offers "rewind to here", which restores the files to that point and continues the conversation from it, the later turns kept in the transcript as rewound. *Accept:* after rewinding past an edit, the file is back to its earlier content and the next turn's model context ends at the chosen message.
- **SES-015** · v1 · **Images in prompts.** Paste or drop up to ten images into the composer; they are scaled down in the app, kept with the session and sent to models and agents that accept images. *Accept:* a pasted screenshot reaches an Anthropic, OpenAI and Gemini model and the Claude Code preset; the transcript shows it after a restart; a fork keeps it; an external agent that declares no image support refuses before anything is sent, saying so, and a model that rejects images fails the turn with the provider's reason.
- **SES-016** · v1 · **Worktree setup and run scripts.** A project names files to copy into each new worktree, a setup command run once when the worktree is made, a run command (such as a dev server) and an archive command; each worktree session gets its own block of ports. The commands run where the agent's do: in a Docker environment, in the session's container (OQ-026). *Accept:* a new worktree session of a trusted project has its `.env` copied and `npm install` run before its first prompt starts, with the output visible; the run command starts in a terminal tab with `FREELOOP_PORT` set; two sessions get different ports; an untrusted project runs nothing.
- **SES-017** · v1 · **Start from a GitHub issue.** The new-session form lists a trusted project's open GitHub issues through the GitHub CLI; choosing one titles the session after it, tags it, and puts the issue's text, comments and link into the first message for the user to edit. *Accept:* choosing issue #12 makes a session titled "#12 …" tagged `issue-12` whose message box holds the issue's body and comments; nothing is sent until the user sends it; local-only mode and an untrusted project list nothing.
- **SES-018** · v1 · **Pull request checks.** After a pull request is opened from a session, the Diff tab shows its CI checks and refreshes them while any run; "Send failures to the agent" puts the failing checks' names, links and the end of their logs into the message box. *Accept:* a failing check shows as failed with its link; the message names it and quotes its log's end; local-only mode checks nothing.
- **SES-019** · v1 · **Attach any file to a message.** Attach, drop or paste files from anywhere on the Mac. A picture goes to the model as a picture (SES-015), text goes in the message within the limits of `@` mentions, and anything else is refused with what to do instead. *Accept:* a text file reaches the prompt and the transcript names it; a PDF is refused with the reason.
- **SES-020** · v1 · **Import an external agent's sessions.** The Import page lists the sessions an external agent keeps by itself, by project or folder, and imports the chosen ones into new sessions. It goes through the agent's protocol (`session/list`, `session/fork`, `session/load`), not its files, so any agent that can list and load is covered the same way, and no model is called. The agent copies the session where it can, and the original stays as it was; one that cannot copy continues the original, and the session says so. What the agent replays becomes the transcript: pictures in messages become attachments, pictures in tool output are left out, and tool calls that never ended show as failed. A replay can ask for nothing and touch nothing. The session then continues the agent's copy, as an external session does after a restart (SES-003). It keeps the title it was imported with, and what it replayed does not count toward usage or activity. *Accept:* a Claude Code session started outside the app, in its command line or desktop app, can be imported and the next prompt reaches the model with the earlier conversation; the original's file is unchanged; a second import of the same session opens the first; a failed import leaves no session; a container environment is refused. Known limit: what the agent compacted away before its last compaction is not replayed, and the session says so.
- **SES-021** · v1 · **Group sessions by when they were last used.** The sidebar groups by project or by last used: Today, Yesterday, Previous 7 days, Previous 30 days, Older, in the user's time zone. Last used is the session's latest recorded event. Rows then name their project. *Accept:* switching changes neither the filter nor what is selected, the choice survives a restart, and two sessions streaming at once do not swap places more than once a minute.
- **SES-022** · v1 · **Finished, not read.** A session whose turn ended while it was out of sight gets a mark on its sidebar row, board card and pane tab until the user sees it. A turn the user stopped or that failed gets none. *Accept:* a session finishing in a covered or hidden pane, or with the window in the background, is marked, and the mark goes when it is on screen in a focused window; one finishing in plain sight is never marked.
- **SES-023** · v1 · **A draft stays until sent or deleted.** What is typed in a session's composer survives going elsewhere in the app, with what is attached, and the text survives a restart. *Accept:* a draft is per session and gone once sent or emptied; what goes to disk is redacted as a transcript is, and attachments stay in memory.
- **SES-024** · later · **Outcomes recorded.** Commits on a session's branch, its worktree merged from the app, and its pull requests merged on GitHub are recorded as events (`commit`, `merged`, `pull_request_state`, and `compare_kept` for the run kept in a compare) and counted with its activity. A pull request's state comes from `gh`, for sessions that have one, at most every 30 minutes for those opened in the last 30 days, never in local-only mode. A finished task is a session with a merged change, or one archived with a commit. Past sessions are counted once from their transcripts and repositories. *Accept:* a commit, a worktree merge and a pull request merged on GitHub each appear in the session's activity; local-only mode makes no `gh` call; past commits are counted.
- **SES-025** · v1 · **A queue of tasks.** Tasks (a prompt, a project, a profile, a worktree by default) wait in a queue and start as sessions when there is room: under the queue's limit on sessions running at once (default 3), with a free slot on the provider (OQ-013), the agent's account limits not at a warning (GUI-028) and any budget not reached (PRV-017). A weekly limit's warning holds only from 95 % used: it comes days before the reset, and holding from it would leave most of the week unused; a shorter window's warning holds at once. A limit that is reached pauses that agent's tasks until its reset time. A held task says which limit, how full it is and until when. Tasks are added on the Queue page (reached from the sidebar's Queue icon, which counts the waiting tasks, and the command palette), with a prompt, a project, a profile and a worktree, and can be reordered, paused and removed. Several GitHub issues at once come later. A started task is an ordinary session tagged `queued`: every tool call asks as usual, and one waiting for an approval counts as running. *Accept:* five tasks with a limit of 2 start two sessions and the next when one ends; a 5-hour limit warning for Claude Code holds its tasks and starts them after the reset, and a weekly one holds them only from 95 %; a task waiting for approval keeps its slot; nothing starts while the queue is paused.

### Permissions and security (SEC)

- **SEC-001** · MVP · **Permission modes per session.** `ask` (default), `accept-edits` (file edits inside the project auto-approved), `plan` (read-only), `auto` (an external agent's own auto mode, for an agent whose preset maps one), `bypass` (everything auto-approved). Bypass must be enabled once in settings. Auto needs a trusted project. Both show a persistent banner and reset to `ask` on new sessions; no file, profile, schedule or fork starts in them. Each ends, with the reason in the transcript, when what allows it goes: the setting, its approval or the project's trust. *Accept:* each mode's behaviour matches this table for a write, a shell call and an MCP call; a session in bypass asks after the setting is turned off, running or not, and after a restart.
- **SEC-002** · MVP · **Rule engine.** Allow and deny rules by tool and pattern: shell command prefix (`shell(git *)`), path glob for file tools, MCP namespace, skill name. Scopes: global, environment, profile, project (`.freeloop/`), session. Deny always wins; more specific scope wins among allows. An allow rule that reached the app's files without being written or approved in the app does not apply until the user approves it. *Accept:* a project deny rule overrides a global allow for the same command; rules are listed with their scope and source file.
- **SEC-003** · MVP · **Single permission broker.** Every permission request from any harness passes through one broker that applies mode and rules, then queues the rest for the user in the attention view. No request is auto-approved by timeout. *Accept:* an ACP agent's permission request and a built-in tool's request look identical in the inbox and in the transcript.
- **SEC-004** · MVP · **Secret storage.** API keys, tokens and environment secrets are stored in the system's keyring: the macOS Keychain, the Windows Credential Manager or the Linux Secret Service; config files hold references only; the UI never shows a stored secret after saving; known secret values are redacted from logs and transcripts. The app's secrets are kept together in one Keychain item, so a rebuild asks for permission once (`secrets.Vault`, OQ-033). *Accept:* config files contain no key material; a vault that cannot be read is never overwritten, and a separate item is removed only after the vault reads back holding it; a secret pasted into chat is redacted in the stored transcript.
- **SEC-005** · MVP · **Protected paths.** By default, writes outside the project root, inside `.git/`, and inside the app's own config directory are denied regardless of mode. Reads are covered by SEC-013. *Accept:* in bypass mode, writing to `~/.ssh/config` is still refused and recorded.
- **SEC-006** · MVP · **Project trust.** First use of a project asks for trust before reading `AGENTS.md`/`CLAUDE.md`, `.freeloop/` config, project skills or project MCP servers. *Accept:* an untrusted project runs with global config only and says so.
- **SEC-007** · MVP · **Audit trail.** Every tool execution, permission decision and mode change is in the transcript with timestamp and actor (user, rule, mode). *Accept:* for any file change the transcript shows which call made it and how it was approved.
- **SEC-008** · MVP · **Process isolation for external harnesses and MCP servers.** Separate processes; environment scrubbed to the configured variables plus a minimal base; stdio only. *Accept:* `env` printed from inside an external harness shows no app secrets other than those configured for its environment.
- **SEC-009** · MVP · **No undeclared network.** Outbound connections only to configured providers, MCP servers, harness endpoints and SSH environments, and to a pinned token optimizer download when the user clicks it (HRN-019); no telemetry; update checks opt-in. *Accept:* with no providers configured, a network monitor shows zero outbound connections from the app over 10 minutes.
- **SEC-010** · MVP · **Untrusted tool output.** The built-in harness frames tool results and fetched content as data; instructions found there never change permission state or trigger actions without the usual approval. *Accept:* an `AGENTS.md`-style instruction planted in a file read by the agent cannot cause an auto-approved write.
- **SEC-011** · v1 · **Sandboxed execution.** Through the Docker environment (ENV-005) or the system's own sandbox (ENV-009; macOS and Linux). *Accept:* per ENV-005 and ENV-009.
- **SEC-012** · v1 · **Pinned dependencies, SBOM, checksums.** Builds are ad-hoc signed, not notarized (OQ-009). *Accept:* the release includes an SBOM and checksums; the README says how to open the downloaded app.
- **SEC-013** · MVP · **Reads outside the project root.** File reads, directory listings and searches outside the session's project root require approval in every mode except `bypass`; a fixed list of never-readable locations (`~/.ssh`, `~/.gnupg`, `~/.aws`, browser profiles, the Keychain database directory, the app's own config directory) is refused in every mode including `bypass`. *Accept:* in `accept-edits` mode a `read_file` of `~/.zshrc` prompts; a read of `~/.ssh/id_ed25519` is refused and recorded even in `bypass`.
- **SEC-014** · v1 · **What the policy held.** A session's Info tab and the usage page's approvals view show what the user's policy stopped that the agent or the repository would have let through: requests a rule denied without asking, requests the user denied, mode changes an agent tried on its own and was refused, reads and writes refused at a protected path, and calls a hook blocked. The Info tab lists each with a jump to the moment in the transcript; the usage page counts them by kind and by session, and opens the session. *Accept:* in a Claude Code session whose repository's `.claude/settings.json` allows `Bash(*)`, a `git push` asks, is denied, and shows under "Held by your policy"; an agent's own switch to bypass shows there as refused; the counts match the transcript; a session with nothing held shows the line at zero, not no line.
- **SEC-015** · v1 · **A repository cannot loosen the policy through an agent's own config.** An external agent started by the app runs under the user's policy whatever the repository's own files for that agent say: allow rules, a default mode, local settings. In a project the user has not trusted, none of the repository's agent hooks run. *Accept:* `make verify-agents` runs each case against the real agent with a policy that refuses: allow rules, a default bypass mode, local settings, a session hook and a tool hook; the remote stays empty and no hook runs in an untrusted project. A control case shows the same push getting through when allowed.
- **SEC-016** · v1 · **"Always" is the app's rule only.** When the user chooses an "always" answer, the app keeps the rule and answers the agent with its "once" option, so the agent saves nothing of its own, in the project or elsewhere. A plan's options are not rules but the mode the agent goes on in: the one chosen goes back as it is, and the broker saves no rule for it (GUI-043). *Accept:* after "Allow always" for a Claude Code `git push`, the project's `.claude/` holds no new rule and the push went through.
- **SEC-017** · v1 · **Reading a secret asks.** A read inside the project of a file whose name says it holds secrets, as the SSH sync judges it, asks the user, except in bypass. *Accept:* reading `.env`, `.env.production`, a `.pem` or an SSH key asks; `.env.example` and ordinary files do not.
- **SEC-018** · v1 · **Would this be allowed?** The policy page (Settings, Policy, which replaced Permission rules) and `freeloop check` say what the broker would do with a call that is not made: allowed, denied or asked, with the reason, the rule that decided and its scope and file, the rules it overruled, allow rules waiting for approval, the hooks that would still run and could deny it, and what the session's agent decides by itself in that mode. It is judged in a session, or in a project as a new session there would be (its profile, environment, trust and mode), by the broker's own code (`Broker.Explain` over the same `decide` as a real request); nothing is recorded, nobody is asked and no hook runs. The page also lists every scope's rules in order, the hooks with their approval, the protected paths and what each agent decides itself, from a preset's `decidesItself`. `freeloop check` exits 0 when allowed, 2 when the user would be asked, 3 when denied and 1 on an error. *Accept:* a test runs every kind of decision through both `Explain` and `Request` and finds them the same; with a global `deny shell(git push *)`, `freeloop check -project . shell git push origin main` prints the rule and exits 3, also with `-mode bypass`; a trusted project's deny shows as deciding with the global allow overruled, and is not applied untrusted; Claude Code in auto mode says its own approvals never reach Freeloop; `make check-app` adds a deny rule on the page and sees the check name it.

- **SET-002** · MVP · **Project-level overrides.** `.freeloop/` in a repo may contain profiles, environment defaults, MCP servers, skills and rules; applied after trust (SEC-006). *Accept:* a project profile appears in the new-session dialog for that project only.

- **SET-005** · v1 · **Backup and export of config without secrets.** *Accept:* restoring the export on a fresh install recreates all providers (prompting for keys) and profiles, and the hooks and agent presets it brings run nothing until the user approves them; nor do its allow rules apply, its environments run, its choice of a token optimizer count, or `permissions.allowBypass` or a profile's `accept_edits` count until then, and nothing is sent to a provider, search or registry address, or a fallback, that it brought. Restoring first shows what it would do, changing nothing until the user agrees; it cannot turn local-only mode off, and it says which deny rules and blocking hooks its files leave out.
- **SET-006** · v1 · **Keyboard shortcut customization.** *Accept:* the palette, Settings, attention, text size, moving between panes (⌃⇧ and the arrows to start with, wrapping around as tmux does) and approval letters can be changed in Settings; a reserved or used key is refused with the reason.

They share one form: what saves itself still does, and what waits for Save (hooks, prices, budgets, web search) is named wherever the Save button shows. ⌘, opens the page last shown; links into the settings open the page they mean. *Accept:* `make check-app` opens each page and finds only its own sections, none longer than 2600 px, and ⌘, back on the page last shown.

### Workflows (WFL)

A workflow is a method of work the app knows the steps of, after Matt Pocock's talk "Full Walkthrough: Workflow for AI Coding" (2026): grill the brief, write a PRD, split it into vertical slices, run the unattended ones one session each, review them, QA by hand and clean up. It is packaged the way token optimizers are (HRN-019): files define it, one ships with the app, and nothing in it runs or installs until the user asks. Decided 2026-11-08 (OQ-038 to OQ-040).

- **WFL-001** · v1 · **Workflows defined by files.** A workflow is `workflows/<id>.yaml` in the data folder: its name, the backlog folder, its stages (a slash command, a title, the mode to switch to, the skill it uses and a prompt template whose placeholders are checked), the skills it needs, and its AFK run's and review's settings (profile, mode, sandbox, issue cap, the commands the run will want allowed). One ships with the app, `plan-slice-afk` ("Plan, slice, run AFK"), with its skills' texts, written for Freeloop. Listing workflows runs nothing; a file's workflow is used only after the user approves it as it is, and any change to the file ends that approval (as for optimizers). A workflow can never ask for bypass or auto mode. *Accept:* parser tests refuse an unknown field, bypass or auto, a command used twice or one of the app's own mode commands, and an unknown placeholder; a file replaces the built-in one of its ID; an approved file edited afterwards waits for approval again.
- **WFL-002** · v1 · **Choosing a workflow and running its stages.** A picker beside the optimizer sets a session's workflow; precedence is the session's choice, then the profile's `workflow:`, then `defaults.workflow` in Settings, with `off` beating the rest; a `workflow_changed` event records it. Each stage is a slash command in the composer (`/grill`, `/prd`, `/slice`, `/afk`, `/review`, `/cleanup` for the built-in one), with whatever follows the command passed to its prompt; the palette has "Start a workflow…" and each stage. A prompt stage switches to its mode and sends its prompt as the user's message, which names its skill; a stage whose workflow is not approved, or whose skills are not installed, says so and sends nothing. The same commands and prompts serve every harness (HRN-001). *Accept:* an engine test sees `workflow_changed` at creation, `off` on a profile beating the default, `/grill add dark mode` send the grill prompt with "add dark mode" in Ask mode (plan mode's own approval read as approving code), and an unapproved workflow's stage refused; `make check-app` chooses the workflow and runs `/slice`.
- **WFL-003** · v1 · **A workflow's skills, installed on request.** Settings → Workflows lists each workflow with its stages, its skills (installed, missing, or changed since installed), what its AFK run will want allowed and its approval. "Install skills" copies the built-in workflow's skills into the app's skill store in one click, recording their source and digest (SKL-005); nothing installs by itself, and nothing is written into `~/.claude` or a project's `.claude/`. *Accept:* installing writes `skills/<name>/SKILL.md` with its provenance, and a second install changes nothing; a skill edited after installing shows as changed; no file outside the data folder is written.
- **WFL-004** · v1 · **The backlog.** A workflow's PRDs and issues are Markdown files in the project's backlog folder (`backlog/prds/`, `backlog/issues/` by default; OQ-039), written by agents like any project file, read by the app only in trusted projects (SEC-006) and only through the environment (ENV-001). An issue's frontmatter has `title`, `status` (`open` or `done`), `type` (`afk` or `human`) and `blockedBy` (other issues' file names). The Board has a Backlog column per trusted project with a backlog, each issue showing its type, status, whether it is ready or what blocks it, and what it blocks. "Archive finished" removes done issues, and PRDs whose issues are all done, from the project in a commit of their own that names them, so git history keeps them and no copy is kept elsewhere (OQ-041). GitHub issues are not a source (OQ-038). *Accept:* a unit test parses frontmatter and finds ready, blocked and cyclic issues; an untrusted project shows no backlog; `make check-app` sees two issues on the Board, one blocked by the other; an engine test archives a done issue and finds it in the commit before, and nothing in the data folder.
- **WFL-005** · v1 · **The AFK run.** Started from the Backlog, the palette, `/afk` or a schedule (SES-012), a run works through the project's unblocked AFK issues one at a time, each as a fresh session queued through SES-025, so the queue's limit, provider slots, account limits and budgets apply. Its sessions share one worktree and branch of the run (OQ-040), so the backlog must be committed first; they start in the workflow's mode (accept edits by default), on its AFK profile, in the sandboxed environment where it is available; each gets the issue, the backlog's state and the recent commits, and is asked to work test-first, run the project's tests and type checks, commit and mark the issue done. Before it starts, the run lists the commands it will want (the workflow's, such as `git commit`, and the project's test and type-check commands) with what the policy says of each now, and the user can allow them for the run's sessions up front, as session rules; nothing is approved for it otherwise, and every other request waits in the attention view (SEC-003). The engine counts an issue done only from its file's status in the worktree, for every harness alike (HRN-001). The run stops when no AFK issue is unblocked, at its issue cap, when a budget is reached, when a session fails or ends without marking its issue done, or when the user pauses or stops it. Starting a run shows the Board, where the run's line and the issue's card say what it is doing; while its issue's session has not started, both say why in the warning colour (the queue paused or full, an agent's limit), and the start dialog says beforehand when the chosen profile's agent is held. *Accept:* engine tests with the scripted provider: two issues, the second blocked by the first, are done in order in one worktree; a session that ends without marking its issue stops the run with the reason; the cap, a reached budget and a pause each stop it; an uncommitted backlog refuses to start; the up-front commands reach the sessions as session rules and nothing else is allowed; a run whose issue waits for a paused queue says so on its step, and `make check-app` sees it on the Board.
- **WFL-006** · v1 · **Review, then QA.** After each issue the run commits what its session left uncommitted, then has the workflow's review profile review the session's changes (HRN-018: read-only, in plan mode, in the run's worktree). When the review has answered, the issue is in the attention view as "Ready for QA" with its session and review, until the user marks it QA'd; QA stays the user's. *Accept:* an engine test sees the review session start after the first issue, the next issue wait for it, and both issues listed as ready for QA; `make check-app` runs the built-in workflow on the demo provider from slicing to two issues ready for QA.
- **WFL-007** · later · **Parallel AFK runs.** One worktree per unblocked issue, up to the queue's limit, then a merge session that brings the branches together and runs the tests. Planned in ROADMAP.md, not built.
- **WFL-008** · v1 · **Guided stages.** A session with a workflow shows a stage strip above its composer: each stage on the workflow's path (those that send a prompt, and the AFK run) as done, running, next or to do, from `workflow_stage` events the engine records when a stage starts, and for the AFK stage from the project's run. A Next button runs the next stage; one marked `needsInput` (the built-in `/grill`) instead waits in the composer for what it is about, and is refused without it. When a stage's turn ends, the strip says which files it wrote. The conversation marks where each stage began. "Start a workflow…" asks what it is about and sends that to the first stage as the session is created. An agent's own command for a skill a stage uses is left out of the `/` menu, so the stage is what is offered. The built-in `/grill` asks before changes rather than plan, since plan mode's own approval reads as approving code. *Accept:* unit tests: the strip's states through a grill, a later turn, a skipped stage and an AFK run; the files a stage wrote; the menu without a stage's skill; an engine test sees `workflow_stage` before the stage's prompt and `/grill` without a brief refused; `make check-app` sees the strip with the grill next, the stage marked in the conversation, the AFK run next after `/slice` with the files it wrote, and starts the run from the Next button.
- **WFL-009** · v1 · **A run in full, and commands of the user's own.** "Show the run", on the Board and in the stage strip, opens the project's run: each issue it took on with its state and why it waits, its session and review, the approvals its session waits for, and QA for what is finished; then the AFK issues still to come; with Pause, Resume and Stop. Starting a run, the user can type in commands to allow beside those offered (one line, never starting with `*`), and the project's other check targets (Makefile targets such as `check-app`) are offered unticked. *Accept:* an engine test: `make check-app` offered as another check, `*` refused, a typed command reaching the run's allowed commands; `make check-app` adds a command of its own and sees both issues in the run view, ready for QA, with their sessions and reviews.
- **WFL-010** · v1 · **A smaller model for the issues.** The AFK run's dialog chooses, beside each profile, the model its issues' and its reviews' sessions switch to; empty keeps the profile's. The choices are the built-in agent's provider models, or the models an external agent last reported in one of the user's sessions, since one says what it offers only once it runs; with none reported the dialog says how to get them. Each session switches through its own model option before its first message, as its model list in the composer does, for every agent alike (HRN-001); a model that cannot be had fails that issue rather than run on a costlier one. *Accept:* an engine test runs both issues and both reviews on a chosen model and refuses one the profile does not offer; `make check-app` finds the profile's models in the dialog and chooses one.
- **WFL-011** · v1 · **Every callable provider's models for a run.** The AFK dialog's model pickers for a built-in profile list every model of every provider the user can call without being asked (it has its key, or needs none), grouped by provider with the profile's own first, from each provider's cached listing, plus "Other model…"; a model on another provider runs the run's sessions there and keeps the rest of the profile. An external agent's profile keeps the models the agent reported. *Accept:* an engine test on two scripted providers lists the second provider's listed models and runs an issue and its review on it; `make check-app` starts a run on the demo's second provider.
- **WFL-012** · v1 · **Effort for a run.** Beside each model in the AFK dialog an Effort picker offers the profile's effort or the levels the chosen model supports, disabled for a model without effort; the run stores it and each session switches through its effort option before its first message, as it does for the model (HRN-001). *Accept:* an engine test runs the issues and the review at the chosen efforts and stores none for a model without effort.
- **WFL-013** · v1 · **Model sets.** A model set names a model and effort, or "not fixed", for a workflow's planning stages, its issues and its reviews; sets are made in Settings and kept in `config.yaml` (`modelSets`), and each workflow picks one set or none (`workflowModelSets`), outside the workflow file, so choosing one never touches a workflow's approval. A set naming a provider that is gone or has no key keeps its value and is shown unavailable. *Accept:* config tests refuse an empty name, a duplicate ID and an unknown effort; an engine test loads a set with a missing provider as unavailable and deleting a set in use clears it from its workflows.
- **WFL-014** · v1 · **Workflows use their set.** A planning stage switches its session to the set's Planning model and effort before its prompt, with a notice, and refuses, offering the current model, when the session cannot have it; a session created with the workflow chosen explicitly starts on the Planning model, one that only takes the default workflow does not; the AFK dialog starts from the set's Issues and Reviews rows, a change applies to that run only, a model the profile cannot have keeps Start disabled, and a run keeps what it started with. Nothing falls back to another model unasked. *Accept:* engine tests for the switch, the refusal, explicit versus default workflow at creation, and a run unchanged by a later edit of its set; `make check-app` makes a set and finds it used by a stage, a new workflow session and the dialog.
- **WFL-015** · v1 · **What a workflow run cost.** From the usage recorded per session and model (PRV-008), a run's cost splits into Planning (its starting session before the run began), Issues and Reviews by model, and each issue's into its session and its review, with its commit; the Board shows both, a pull request drafted from the run's branch carries the line, and the Usage page groups by run with `run`, `issue` and `commit` in its export. Unpriced usage is shown as such, never as nothing. *Accept:* engine tests of the breakdown with scripted usage, including the planning cut-off and unpriced models; `make check-app` finds the cost line on the Board and the run on the Usage page.

### Extensibility (EXT)

- **EXT-001** · MVP · **File- and process-based extension points only.** Profiles, skills, MCP servers, providers, environments and harnesses are configured through files and processes; no in-process plugin loading. *Accept:* every extension type in this document can be added without rebuilding the app.
- **EXT-002** · MVP · **Documented event schema.** A versioned JSON schema for session events (message deltas, thinking, tool call lifecycle, permission request and decision, plan, mode, usage, error, end). Transcripts use it; the GUI consumes it; external harness events are mapped to it. *Accept:* `schemas/events.json` validates every transcript produced by the test suite.
- **EXT-003** · v1 · **Harness SDK templates.** Python and Go templates that speak ACP, with a test harness. *Accept:* per HRN-011.
- **EXT-004** · v1 · **Headless control.** Local JSON-RPC API over a Unix socket and a small CLI (`freeloop sessions list`, `freeloop prompt <id> "..."`). *Accept:* a session created from the CLI appears in the GUI live.
- **EXT-005** · v1 · **Hooks.** Shell hooks on session start, before and after tool use, and on permission request, per profile or project, with the event as JSON on stdin and a documented exit-code contract. *Accept:* a pre-tool hook can block a shell command with a message shown in the transcript; a hook that reached the app's config files without being written or approved in the app runs nothing until approved; a pre-tool or permission-request hook that times out, cannot start or exits other than 0 or 2 makes the call ask with the reason, in every mode, bypass included; a trusted project's hooks that changed since it was trusted run nothing until approved.
- **EXT-006** · later · **UI plugins.**
- **EXT-007** · later · **Out-of-process provider adapters.**

## Non-functional requirements

### Performance (NFR-PERF)

- **NFR-PERF-001** · MVP · UI remains interactive (input latency under 100 ms) with ten sessions streaming concurrently on an M1 with 16 GB.
- **NFR-PERF-002** · MVP · Opening a 5,000-event transcript renders in under 1 s; scrolling is virtualized.
- **NFR-PERF-003** · MVP · Cold start to usable window under 2 s; restoring 50 archived and 10 active sessions under 3 s.
- **NFR-PERF-004** · v1 · Idle memory under 300 MB for the app with ten idle sessions, excluding external harness processes.
- **NFR-PERF-005** · MVP · Streaming tokens appear within 50 ms of arrival from the provider.

### Security (NFR-SEC)

- **NFR-SEC-001** · MVP · Secrets only in the Keychain (SEC-004); no secret material in logs, crash reports or exports.
- **NFR-SEC-002** · MVP · Every side-effecting action is attributable in the transcript (SEC-007).
- **NFR-SEC-003** · MVP · Threat model documented in `docs/SECURITY.md` before the first public release: prompt injection, malicious skills, malicious MCP servers, hostile repos, local attacker with the same user account.
- **NFR-SEC-004** · v1 · Builds are reproducible from a tagged commit; dependencies pinned with checksums.
- **NFR-SEC-005** · v1 · Sandboxing available for shell execution (Docker environment, or the native sandbox, ENV-009).

### Privacy (NFR-PRIV)

- **NFR-PRIV-001** · MVP · No telemetry, analytics or crash reporting leaves the machine. Diagnostics are local files the user can share manually.
- **NFR-PRIV-002** · MVP · Transcripts, config and indexes are stored locally only; export is an explicit user action.
- **NFR-PRIV-003** · MVP · The app sends to a provider only what the user can see in the transcript plus the system prompt, tool definitions and skill index, which are inspectable. Every model call a session makes goes through the engine's provider wrapper, which writes a `model_context` event to the transcript whenever what the call carries besides the conversation changes: the kind of call (a turn, compaction, a commit message, a pull request text, a handoff summary), provider, model, effort, system prompt and tool definitions, and for the app's own calls what else they sent, in words. The store redacts it like any event. The session's Info tab shows it as "What the model sees", in plain text. An agent that builds its own requests records none, and the tab says so. *Accept:* a built-in session's first turn records the system prompt with the project's AGENTS.md and the tools; a turn that changes nothing records nothing; plan mode records a new one; a commit message records its own with "The session's diff"; a known secret in AGENTS.md is redacted; `make check-app` reads the prompt's sections and tools in the Info tab, and the Claude Code session's message.

### Offline and local-only operation (NFR-OFF)

- **NFR-OFF-001** · MVP · With a local model provider and local MCP servers, every MVP feature works with networking disabled, except features that are inherently remote (remote MCP servers, git push, PR creation).
- **NFR-OFF-002** · MVP · No startup network dependency; no feature degrades because an update check or remote asset failed.
- **NFR-OFF-003** · v1 · A "local-only" switch blocks all non-loopback outbound connections from the app and reports attempts.

### Cross-platform (NFR-XPLAT)

- **NFR-XPLAT-001** · MVP · Supported: macOS 14 and newer, on Apple Silicon only (decided 2026-11-08). The app is built for `arm64` alone and says so in its `Info.plist`, so an Intel Mac refuses to open it with the system's own message. *Accept:* the packaged binary's only architecture is `arm64` (`lipo -archs`, checked by `make package`), and `LSMinimumSystemVersion` is 14.0.0.
- **NFR-XPLAT-002** · MVP · No system-specific code outside a platform package (`internal/platform/darwin`, `linux`, `windows`) and the environment layer's per-system files; keyrings, the sandbox, the process table and openers are behind interfaces, so the engine does not change per system.
- **NFR-XPLAT-003** · v1 · **Windows and Linux, working as on a Mac** (raised from later on 2026-11-08: the user wants all three before the repository goes public; OQ-045). Windows 10 1809 or later and Windows 11, on x64 and arm64; Linux with GTK 3 and WebKitGTK 4.1, on x64 and arm64. Every feature behaves the same, with each system's conventions: the primary shortcut key is Ctrl on Windows and Linux; secrets go to the Credential Manager on Windows and the Secret Service on Linux (SEC-004); commands run through Git Bash on Windows (OQ-043) and the user's POSIX login shell on Linux (OQ-019); the terminal runs on ConPTY on Windows; what a session started ends with the app, through job objects on Windows and the ledger of process groups elsewhere (NFR-REL-005); a file read or written through a link or junction swapped in since its check fails on all three. *Differences that remain:* no native sandbox on Windows yet, where "Local, sandboxed" says so and the Docker environment is the confined one (OQ-044); an SSH environment on Windows opens a connection per command, since Windows' OpenSSH cannot share one; a sandboxed command on Linux reaches the host's localhost only with `pasta` installed and, for Ubuntu 24.04's pasta, a network connection, and over TCP only, otherwise just the sandbox's own loopback (OQ-037). *Accept:* the Go tests pass on macOS, on Linux and on a Windows runner with Git Bash; the app builds as a DMG, as a Windows installer and portable zip for both architectures, and as an AppImage and a .deb for both architectures; on each system a session of the demo provider runs a command, edits a file, stores a key in the system's keyring and opens a terminal.

### Accessibility (NFR-A11Y)

- **NFR-A11Y-001** · MVP · Full keyboard operation of conversation, approvals and session switching; visible focus.
- **NFR-A11Y-002** · MVP · Labels for all controls, announced status changes for approvals, contrast at WCAG AA, respects reduced motion, and all text follows the app's Font size setting, also from ⌘+ and ⌘- (OQ-027: web content in a macOS app does not follow the system's Text Size by itself).
- **NFR-A11Y-003** · v1 · VoiceOver pass of all MVP screens with issues fixed.

### Reliability and maintainability (NFR-REL)

- **NFR-REL-001** · MVP · A GUI crash never loses transcript events already received (SES-002); sessions recover on relaunch.
- **NFR-REL-002** · MVP · An external harness or MCP server crash is isolated to its session and shown as an error; the next message starts the agent again.
- **NFR-REL-003** · MVP · Engine packages have unit tests; the provider and ACP layers have replayable fixtures; CI runs the tests on every commit (on Linux, for what macOS minutes cost on a private repository) and the macOS build, lint and real-app check on every tag, weekly and by hand.
- **NFR-REL-004** · v1 · Contributor documentation: architecture overview, how to add a provider, a harness preset, an environment.
- **NFR-REL-005** · v1 · Nothing outlives a crash. Every command, agent, MCP server, sync and terminal the app starts is a process group recorded in `running.json` in the data folder while it runs, with when its first process started; the next start stops, before anything else starts, each group whose leader is still that very process (asked to end, killed two seconds later), and never a process that only got the same number. Only the program's name is recorded, since a command line can carry a secret. *Accept:* a `sleep` left running when an engine is dropped without closing is stopped when the next engine opens the folder; one whose recorded start time differs is left alone; a command that ended is no longer recorded.
- **NFR-REL-006** · v1 · **A build says which commit it is from, and one command leaves one current copy.** Every build made from a repository carries the short commit it was made from, with `+dirty` when the files had changes that were not committed: linked into the binary on every system (`engine.BuildCommit`), written into the Mac bundle's `Info.plist` as `FreeloopCommit` before it is signed, shown in Settings under Data ("This build") and on the first line of the problem report. A development build reads Go's own record of the repository instead. On a Mac, `make install` quits Freeloop (never forcing it, and refusing to run inside it), puts the old bundle in the Trash, builds, checks that the new bundle is validly signed and says this checkout's commit, optionally moves it to `INSTALL_DIR`, and puts every other bundle with the app's identifier (found through Spotlight and in the two Applications folders) in the Trash, so the copy that opens is the current one. A failed build or a bundle of another commit puts the old bundle back. *Accept:* engine tests give the label for a linked-in commit, for Go's record, for uncommitted changes and for none; script tests, in a throwaway repository, replace the old bundle and keep it in the Trash, leave one copy and Trash the strays, restore the old bundle after a failed build or a stamp that is not the checkout's, refuse while the app stays open (leaving it running) and refuse to run inside it; `make check-app` finds the version and the checkout's commit in Settings and in the report.

## Cut from MVP, and why

- Docker, SSH and sandboxed environments (ENV-005 to ENV-010, ENV-009 since built): the local folder covers the daily workflow; environments are the largest matrix of edge cases and would double the MVP.
- Verified presets for Gemini CLI, Codex CLI, Goose, OpenCode (HRN-007): the generic ACP client ships in MVP, so these are configuration plus quirk handling, best done once real users ask.
- Custom code harnesses and the SDK (HRN-011, EXT-003): declarative profiles cover the "switch harnesses" need for the first months; the SDK is cheap once ACP is stable in the app.
- Worktree per session and PR creation (SES-010, SES-011): the primary workflow is parallel sessions across repos, not within one repo.
- Integrated terminal, file tree, command palette, multi-window (GUI-012 to GUI-015): nice to have; each is a week of polish.
- Full-text search, export, fork (SES-007 to SES-009): list and filter suffice for the first release.
- MCP OAuth, resources, prompts, elicitation (MCP-006 to MCP-008): the tool path covers most servers.
- Cost estimates, caching, retries, reasoning controls, native Gemini/Responses providers (PRV-008 to PRV-012): the compatible layer gets every model working; optimizations follow.
